# 4. Хранилище пользовательских настроек

Статус: принято (владелец, 2026-11-11). Начинаем с файлов; IMAP METADATA — запланированный второй вариант.

## Контекст

Часть настроек не помещается в сам ящик и не относится к сессии: плотность списка, язык интерфейса, цвета меток, позже подписи и доверенные отправители для картинок. Их нужно хранить на сервере по ящику, чтобы они переживали выход из системы и работали с разных устройств.

Ограничения:

- Vinette — шлюз без собственной базы; почта остаётся на сервере пользователя.
- Каталог данных и так обязателен: ключи Data Protection должны лежать на постоянном хранилище, иначе после перезапуска все сессии теряются (том `/data` в Docker, `/var/lib/vinette` под systemd).
- Целевая среда — типовой Postfix + Dovecot, где расширение IMAP METADATA (RFC 5464) работает только после настройки `mail_attribute_dict` и ограничивает размер значений.
- Потеря настроек неприятна, но безопасности не затрагивает.

Рассмотрены варианты:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Файлы в каталоге данных | Работает с любым почтовым сервером без настройки, без новых зависимостей, том уже обязателен | Состояние на стороне Vinette: несколько экземпляров должны делить каталог |
| IMAP METADATA | Данные у почтового провайдера, Vinette остаётся без состояния, подходит для нескольких экземпляров | Нужна поддержка и настройка на сервере; лимиты на размер; нужен запасной путь, если расширения нет |
| SQLite | Надёжные транзакции и запросы | Новая зависимость и ещё одно хранилище при том же ограничении «один экземпляр»; для нескольких ключей на пользователя избыточно |

## Решение

1. В `Vinette.Core` — интерфейс `IUserSettingsStore` (`GetAsync`, атомарный `UpdateAsync(mailbox, change)`, `DeleteAsync`) и модель `UserSettings` с проверкой пределов (длины, число меток, допустимые символы). Новые настройки добавляются полями с значением по умолчанию: документ более старой версии читается, более новая версия неизвестные поля игнорируется.
2. Первая реализация — `FileUserSettingsStore` (в `Vinette.Api`): по JSON-документу на ящик в каталоге `Settings:Path`.
   - Имя файла — SHA-256 адреса в нижнем регистре, чтобы список каталога не показывал, кто пользуется системой.
   - Запись атомарна (временный файл → замена), изменения одного ящика сериализуются.
   - Права: каталог и файлы доступны только пользователю процесса (Unix).
   - Повреждённый или слишком большой (> 256 КиБ) файл откладывается рядом как `*.damaged-<время>`, пользователь получает значения по умолчанию; содержимое и имя в лог не попадают.
3. Хранилище выбирается ключом `Settings:Store` (сейчас единственное значение `File`), по образцу `Session:Store`. Каталог — `Settings:Path`; в Docker `/data/settings`, под systemd `/var/lib/vinette/settings`; пустое значение даёт каталог в данных учётной записи и предупреждение в логе.
4. Второй вариант — `ImapMetadata` (хранилище в самом ящике) — добавляется отдельной задачей, когда понадобится несколько экземпляров (VIN-088) или администраторы попросят хранить настройки у почтового провайдера.

## Последствия

- Настройки лежат на диске Vinette: том `/data` нужно сохранять и включать в резервные копии (VIN-132). Потеря каталога сбрасывает настройки к значениям по умолчанию, но не ломает вход и почту.
- Один экземпляр или общий каталог на файловой системе с блокировками; блокировки внутри процесса, между процессами их нет. Несколько экземпляров на разных узлах — только после `ImapMetadata`.
- Интерфейс в Core не знает о хранилище: смена или добавление реализации не затрагивает вызывающий код.
- Секреты (пароли, токены) в настройках не хранятся; хранение учётных данных — отдельный разговор с владельцем.
- Адрес ящика не попадает в имя файла, но в самих документах адреса нет; удаление пользователя сводится к `DeleteAsync`.
