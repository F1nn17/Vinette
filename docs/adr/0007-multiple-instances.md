# 7. Несколько экземпляров за одним адресом: без backplane, без липкой маршрутизации

Статус: принято (владелец, 2026-11-14).

## Контекст

VIN-088: можно ли запускать несколько экземпляров Vinette за одним адресом (балансировщик), и нужен ли для этого Redis backplane SignalR. Что есть к этому моменту:

- сессии можно хранить в Redis (`Session:Store=Redis`), тогда любой экземпляр узнаёт сессию по cookie;
- пароль в сессии зашифрован Data Protection: другой экземпляр расшифрует его только с теми же ключами (`DataProtection:KeysPath` — общий каталог);
- настройки пользователя лежат в файлах (`Settings:Path`, [ADR-0004](0004-user-settings-storage.md)); блокировки у них только внутри процесса, запись атомарна (временный файл и замена);
- события почты рассылаются **каждому подключению отдельно** тем экземпляром, на котором оно открыто ([ADR-0006](0006-mailbox-watching.md)): ни групп, ни рассылки «всем подключениям пользователя с любого экземпляра» у нас нет.

Redis backplane нужен SignalR, чтобы отправка, начатая на одном экземпляре, дошла до подключения на другом (группы, `Clients.All`). Мы так не отправляем. Поэтому backplane не даёт ничего. А вот для самого подключения у SignalR есть требование, которого backplane не снимает: запрос согласования (`negotiate`) и открытие соединения после него должны попасть на один и тот же экземпляр (состояние соединения живёт в памяти), то есть нужна «липкая» маршрутизация.

## Решение

1. **Несколько экземпляров поддерживаются без Redis backplane.** Новая зависимость (`Microsoft.AspNetCore.SignalR.StackExchangeRedis`) не добавляется.
2. **Клиент открывает обычный WebSocket без согласования** (`skipNegotiation`, только транспорт WebSockets): первый же запрос — это само соединение, и его может принять любой экземпляр. Сессию он проверяет по cookie (она в Redis), пароль для слежения за ящиком расшифровывает общими ключами.
3. **Условия многоэкземплярного запуска** (в документации администратора):
   - `Session:Store=Redis` и общий Redis;
   - общий каталог ключей Data Protection (`DataProtection:KeysPath`) и общий каталог настроек (`Settings:Path`), доступные всем экземплярам (общий том); файл настроек не портится при одновременной записи (она атомарна), но два экземпляра, меняющих настройки одного пользователя в одну секунду, перезаписывают друг друга (побеждает последняя запись) — для такой нагрузки нужен `ImapMetadata`;
   - балансировщик пропускает WebSocket (заголовки `Upgrade` и `Connection`); липкость не нужна.
4. **Что остаётся на каждый экземпляр отдельно** (и это записано как ограничение): пределы соединений (`Imap:MaxConnections*`, `Imap:MaxIdleConnections`) считаются на экземпляр, поэтому общее число соединений с Dovecot — их сумма (для `mail_max_userip_connections` учитывать все экземпляры); слежение за ящиком (IDLE) держит каждый экземпляр, на котором есть подключения этого ящика; ограничение попыток входа считается на экземпляр.

## Последствия

- Прокси без поддержки WebSocket оставляет страницу без живых обновлений (плашка «Нет связи» это показывает, всё остальное работает). Запасных транспортов SignalR (long polling) у нас больше нет; для одного экземпляра это малое изменение, для нескольких — цена отсутствия липкости.
- Задач на группы SignalR или рассылку с другого экземпляра пока нет; если появятся (серверные уведомления «всем устройствам пользователя»), backplane возвращается в рассмотрение новым ADR.
- Общий Redis — единая точка отказа сессий: при его недоступности входы и запросы получают ошибку (как у любой общей базы).
- Настройки пользователя в общем каталоге остаются узким местом (нет межпроцессных блокировок, ADR-0004); решение — `ImapMetadata`, отдельная будущая задача. Экземпляры на разных узлах с общим каталогом по сети — на риске администратора.
