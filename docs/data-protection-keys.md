# Ключи Data Protection: хранение и шифрование

Vinette шифрует пароль почтового ящика (пока идёт сессия и пока ждёт отправки отложенное письмо) ключами ASP.NET Core Data Protection. Ключи лежат в каталоге `DataProtection:KeysPath`. Без них сохранённые пароли расшифровать нельзя, а с ними — можно, поэтому каталог с ключами нужно беречь так же, как сами пароли.

По умолчанию файлы ключей лежат открытым XML: защищает их только то, что каталог читает один пользователь процесса. Этого мало, если каталог попадает в резервную копию, на общий том или к кому-то ещё. Поэтому ключи можно **зашифровать сертификатом**: каталог без сертификата ничего не открывает, а сертификат хранится отдельно, как секрет.

## Что настроить

| Ключ | Что это |
| --- | --- |
| `DataProtection:KeysPath` | Каталог ключей. Постоянный (том `/data/keys` в образе); без него все сессии теряются при перезапуске |
| `DataProtection:CertificatePath` | Файл `.pfx` (сертификат с закрытым ключом). Если задан, ключи на диске шифруются им |
| `DataProtection:CertificatePasswordFile` | Файл с паролем от `.pfx` (секрет Docker или Kubernetes); последний перевод строки отбрасывается. Главнее `CertificatePassword` |
| `DataProtection:CertificatePassword` | Пароль от `.pfx` значением или переменной окружения. У файла без пароля — пусто |
| `DataProtection:PreviousCertificatePaths` | Прежние сертификаты (список `.pfx` с тем же паролем), только для чтения старых ключей при смене сертификата |

`CertificatePath` без `KeysPath` — ошибка. Если сертификат задан, но не читается (нет файла, неверный пароль, нет закрытого ключа), **приложение не запускается** и пишет, какую настройку исправить (пароль в сообщение не попадает): оно не должно молча начать писать ключи открытыми. Пока `CertificatePath` не задан, при запуске в журнале предупреждение «keys are stored unencrypted».

## Как сделать сертификат

Подойдёт самоподписанный: он нужен только как ключ шифрования, его никто не проверяет.

```bash
openssl req -x509 -newkey rsa:3072 -nodes -keyout key.pem -out cert.pem -days 3650 -subj "/CN=vinette-keys"
openssl pkcs12 -export -inkey key.pem -in cert.pem -out vinette-keys.pfx
# спросит пароль; запишите его в файл секрета:
printf '%s' 'ваш-пароль' > pfx-password
shred -u key.pem cert.pem 2>/dev/null || rm key.pem cert.pem
```

Храните `vinette-keys.pfx` и пароль **отдельно от каталога ключей и от его резервных копий**: если они лежат рядом, шифрование ничего не даёт. Резервную копию самого сертификата сделайте обязательно: без него ключи, а значит и сохранённые пароли, не прочитать (пользователям придётся войти заново, письма из очереди отложенной отправки попадут в «Черновики»).

## Docker Compose

```yaml
services:
  vinette:
    image: ghcr.io/f1nn17/vinette:latest
    environment:
      VINETTE_DataProtection__KeysPath: /data/keys
      VINETTE_DataProtection__CertificatePath: /run/secrets/vinette-keys.pfx
      VINETTE_DataProtection__CertificatePasswordFile: /run/secrets/vinette-keys-password
    secrets:
      - vinette-keys.pfx
      - vinette-keys-password
    volumes:
      - vinette-data:/data
secrets:
  vinette-keys.pfx:
    file: ./secrets/vinette-keys.pfx
  vinette-keys-password:
    file: ./secrets/pfx-password
volumes:
  vinette-data:
```

В Kubernetes те же два файла кладутся в Secret и монтируются в `/run/secrets`. На голом железе — файлы с правами `600` у пользователя `vinette` в `/etc/vinette`.

## Что произойдёт при включении

- Новые ключи пишутся зашифрованными. Каталог можно проверить: в файле `key-*.xml` нет `<masterKey`, есть `EncryptedData`.
- **Ключи, которые уже лежат открытыми, продолжают читаться** (чтобы сессии и очередь отложенных писем пережили включение), но остаются открытыми в своём файле, пока не истекут (ключ живёт 90 дней, затем создаётся новый). Чтобы зашифрованным стал весь каталог сразу, остановите приложение, перенесите старые файлы `key-*.xml` в другое место и запустите: будет создан новый, зашифрованный ключ. Цена: сохранённые пароли не расшифруются, то есть все войдут заново, а письма из очереди отложенной отправки уйдут в «Черновики». Перенесённые файлы после этого удалите.
- При нескольких экземплярах у всех один каталог ключей и один сертификат.

## Смена сертификата

1. Сделайте новый `.pfx` (см. выше).
2. Укажите его в `CertificatePath`, а прежний добавьте в `PreviousCertificatePaths` (пароль у них общий; если у нового пароль другой, задайте один и тот же при экспорте).
3. Перезапустите. Старые ключи читаются прежним сертификатом, новые пишутся новым.
4. Старые ключи остаются зашифрованными старым сертификатом, пока не истекут (до 90 дней, плюс время жизни самих сессий). Когда все старые ключи сменились, уберите прежний сертификат из `PreviousCertificatePaths` и уничтожьте его файл.

Если сертификат скомпрометирован, а не просто истёк, считайте скомпрометированными и ключи: замените сертификат и сделайте то, что описано выше для старых ключей (перенос файлов), затем смените пароли ящиков, если каталог ключей мог попасть к постороннему вместе с сохранёнными сессиями.

## Как проверить

```bash
# в журнале при запуске:
#   "The Data Protection keys are encrypted with the certificate /run/secrets/vinette-keys.pfx ..."
docker logs vinette 2>&1 | grep -i "Data Protection keys"
# в каталоге ключей нет открытого ключа:
grep -L "EncryptedData" /путь/к/keys/key-*.xml    # должен ничего не вывести для новых ключей
```
