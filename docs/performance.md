# Производительность

Что читатель ждёт и сколько скачивает, какие у этого бюджеты и как это проверяется (VIN-131). Бюджет — предел, при превышении которого проверка в CI падает; он выбран примерно втрое выше измеренного, чтобы медленная машина проходила, а изменение, замедляющее что-то на порядок, нет.

## Размер того, что скачивает браузер

Проверяется после сборки: `make check-bundle` (входит в `make check`, а значит и в CI). Размеры — gzip, уровень 9, КБ по 1024 байта; шрифты в бюджет не входят (8 файлов woff2 примерно по 7–12 КБ, грузятся только те начертания, которые нужны странице).

| Что | Измерено | Бюджет |
| --- | --- | --- |
| JavaScript первой загрузки (то, что называет `index.html`) | 196,8 КБ | **230 КБ** |
| Самый большой JavaScript, который грузится позже (редактор письма) | 133,9 КБ | **160 КБ** |
| Весь JavaScript приложения | 330,7 КБ | **400 КБ** |
| Весь CSS | 7,6 КБ | **12 КБ** |

Скрипт: [scripts/check-bundle-size.mjs](../scripts/check-bundle-size.mjs), бюджеты — в [scripts/bundle-size.mjs](../scripts/bundle-size.mjs) (тест проверяет, что они совпадают с этой таблицей). Если проверка упала: в сообщении названа превысившая цифра и три самых больших файла; ищите, что выросло (библиотека, или импорт тяжёлого модуля, который попал в первую загрузку), а поднимать бюджет можно только с причиной, записанной здесь.

### Что нашли при измерении

Редактор письма (ProseMirror, около 140 КБ gzip) должен грузиться только на экране «Написать». Но страница почты брала быстрый ответ из «barrel»-файла фичи (`features/compose/index.ts`), который заодно подтягивает и редактор, и он попал в **первую загрузку**: **340,8 КБ вместо 204 КБ** (на 40 % больше). Исправлено прямым импортом (`@/features/compose/QuickReply`); редактор снова грузится только вместе с экраном написания. Правило записано в [AGENTS.md](../AGENTS.md): код первой загрузки не импортирует тяжёлое через barrel фичи.

## Время ответа на большом ящике

Проверка на **50 000 писем** в одном ящике, на настоящем Dovecot: [LargeMailboxIntegrationTests](../backend/tests/Vinette.Mail.Tests/LargeMailboxIntegrationTests.cs) (интеграционные тесты, `make test-integration`; в CI их гоняет job «Integration tests»). Письма создаются прямо в каталоге ящика внутри контейнера (50 000 файлов за 4 секунды), Dovecot строит индекс, затем замеряются операции, которые читатель делает чаще всего. Числа проверяют и корректность: сколько найдено, сколько непрочитанных, что страницы идут подряд.

| Операция на ящике из 50 000 писем | Измерено | Бюджет |
| --- | --- | --- |
| Первая страница при первом обращении к папке (Dovecot строит индекс) | 1,25 с | 30 с |
| Первая страница без начала текста | 0,25 с | 2 с |
| Первая страница с началом текста (список писем) | 0,38 с | 2 с |
| Страница глубоко в папке (около самых старых писем) | 0,97 с | 4 с |
| Страница в середине папки | 1,08 с | 4 с |
| Список папок со счётчиками | 1,04 с | 4 с |
| Первая страница «Непрочитанных» (5 000) | 1,13 с | 4 с |
| Первая страница «С флажком» | 1,07 с | 4 с |
| Поиск по теме (редкое слово) | 2,36 с | 8 с |
| Поиск по отправителю | 1,43 с | 6 с |
| Поиск по тексту (редкое слово, без полнотекстового индекса) | 2,04 с | 15 с |
| Поиск по тексту русского слова | 2,00 с | 15 с |
| Открыть одно письмо | 1,08 с | 4 с |

Это время работы приложения с почтовым сервером (запрос к Dovecot и разбор ответа), то есть то, что видит читатель за вычетом сети до браузера. Условия: Windows 11, Docker Desktop (WSL2), Dovecot 2.4 в `docker-mailserver`, письма по 500 байт; на другом железе и с другими письмами числа будут другими, поэтому бюджеты с запасом.

### Как устроен список на большом ящике

- Список читается страницами по 50 писем (курсор по UID, а не номер страницы): глубина папки на размер страницы не влияет, а новая почта не сдвигает страницы.
- Для середины и конца папки нужно найти положение курсора среди писем: это один поиск на сервере, он и составляет разницу между первой страницей (0,25 с) и глубокой (около 1 с).
- Фильтры и поиск выполняет сервер одной командой `SEARCH` (в ответе только номера), страницу из найденных номеров приложение вырезает само и запрашивает только её письма ([architecture.md](architecture.md)).
- Поиск по тексту без полнотекстового индекса просматривает письма на сервере: на 50 000 коротких писем это 2 секунды, но на ящике с большими письмами и сотнями тысяч писем время растёт пропорционально. Для таких ящиков включите на Dovecot полнотекстовый поиск (плагин `fts`: Flatcurve, Xapian, Solr или другой): Vinette обращается к нему через тот же `SEARCH` и ничего менять не нужно.
- Ограничения для защиты от тяжёлых запросов: до 8 слов и 200 знаков в запросе, одна страница не больше 100 писем.

## Как повторить

```bash
make build && make check-bundle                        # размер
make test-integration                                  # время на 50 000 писем (нужен Docker; около минуты)
VINETTE_PERF_REPORT=perf.txt make test-integration     # то же, и таблица времени сохранится в perf.txt
```

## Чего здесь нет

- **Время до первого экрана в браузере** (загрузка, разбор, отрисовка) не измерялось: на него влияют сеть и устройство. Размер первой загрузки (≈ 200 КБ gzip) и ленивая загрузка редактора — то, на что приложение влияет само.
- **Нагрузка многих пользователей сразу.** Измерен один читатель на большом ящике. Пределы для многих — число соединений с почтовым сервером (`Imap:MaxConnections*`, [admin-guide.md](admin-guide.md)) и ограничения самого почтового сервера.
- **Ящики больше 50 000 писем** и письма большого размера (для них есть `Imap:MaxViewableMessageBytes`).
