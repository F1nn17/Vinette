# Архитектура

Vinette — шлюз между браузером и почтовым сервером. Браузер не умеет работать с IMAP/SMTP, поэтому бэкенд держит соединения с почтовым сервером от имени пользователя и отдаёт фронтенду обычный REST API и real-time события.

## Схема

```text
┌──────────┐  HTTPS   ┌────────────────────────────────────┐  IMAP 993 (TLS)        ┌─────────┐
│ Браузер  │ ───────▶ │ Vinette (ASP.NET Core, один процесс)│ ─────────────────────▶ │ Dovecot │
│ (SPA)    │ ◀─────── │  • REST       /api/v1               │                        └─────────┘
└──────────┘          │  • SignalR    /hubs/mail            │  SMTP submission       ┌─────────┐
                      │  • статика SPA (wwwroot)            │ ─────────────────────▶ │ Postfix │
                      └────────────────────────────────────┘  587 STARTTLS / 465 TLS └─────────┘
```

Решения о нагрузке и безопасности — ниже. Rspamd работает на стороне почтового сервера и Vinette напрямую не используется.

## Проекты бэкенда

| Проект | Назначение |
| --- | --- |
| `Vinette.Api` | Хост: endpoints, SignalR hub, раздача SPA, конфигурация, health |
| `Vinette.Core` | Доменные модели и интерфейсы; без зависимости от MailKit |
| `Vinette.Mail` | IMAP/SMTP на MailKit, разбор MIME, санитайз HTML |

Зависимости: `Api → Core, Mail`; `Mail → Core`. `Core` ни от чего не зависит.

## Соединения с IMAP

- На каждую веб-сессию — одно рабочее IMAP-соединение (запросы API); на каждый **ящик** — одно общее IDLE-соединение для слежения за «Входящими» (события о новых письмах, транслируются через SignalR), решение — [ADR-0006](adr/0006-mailbox-watching.md).
- Соединения живут в пуле с таймаутом простоя; по истечении закрываются и открываются заново при следующем обращении.

## Идентификатор письма

В API письмо идентифицируется тройкой `(folder, uidValidity, uid)` — никогда не порядковым номером (sequence number). Смена `uidValidity` делает прежние идентификаторы недействительными, клиент обязан это обработать.

В коде это `Vinette.Core.Mail.MessageId`. В API идентификатор — одна непрозрачная строка `base64url(папка).uidValidity.uid`, например `SU5CT1g.1731000000.42`: без `/`, `+`, `=`, поэтому годится для пути URL; форма канонична (один текст на один идентификатор, ведущие нули, знак и «хвостовые» биты base64 отвергаются), так что идентификаторы можно сравнивать и кэшировать как текст. Маршруты принимают `MessageId` напрямую (`IParsable`), в JSON он — та же строка; некорректный идентификатор — 400. Операции с письмом перед работой сверяют `uidValidity` из идентификатора с текущим значением папки (`MessageId.EnsureCurrent`); при расхождении — `UidValidityChangedException`, ответ `409 uid_validity_changed`, а клиент (`onMailOutdated` в `shared/api/client.ts`) сбрасывает всё закэшированное из ящика.

## Папки

`GET /api/v1/folders` отдаёт плоский список папок уже в порядке сайдбара (`FolderOrder`): Входящие, Черновики, Отправленные, Архив, Спам, Корзина, затем папки пользователя по имени, дети сразу за родителем. Иерархию восстанавливает `parentPath`; идентификатор папки во всех маршрутах — `path` (полное имя с разделителями сервера, в Unicode, не modified UTF-7). Роль берётся из SPECIAL-USE-атрибутов сервера; догадки по именам для серверов без SPECIAL-USE и локализованные названия — VIN-040. Счётчики (`total`, `unread`) — одним запросом LIST-STATUS, если сервер умеет (иначе MailKit спрашивает STATUS по папке); у папок-«контейнеров» (`\Noselect`) они 0. INBOX всегда в списке один раз. Имена в Unicode даёт MailKit (modified UTF-7 по проводу декодируется им; кириллические папки проверены на настоящем Dovecot). Если сервер не отдаёт SPECIAL-USE, роли добавляет `FolderRoleGuesser`: по именам (английским и русским, без учёта регистра) в корне или внутри `INBOX`, `[Gmail]`, `[Google Mail]`; роль, уже названная сервером, не меняется и достаётся одной папке. Названия специальных папок на экране берёт клиент по `role` (`folderLabel`, ключи `folders.*`), поэтому «Gesendet» и «Sent Items» показываются как «Отправленные»; свои папки пользователя называются как есть. Путь к почте — `IMailGateway.ExecuteAsync` → `IMailSession.GetFoldersAsync`; учётные данные эндпоинт берёт из сессии (`GetMailCredentials`).

## Список писем

`GET /api/v1/folders/{folder}/messages?limit&after&order` — страница списка. `{folder}` — `path` папки, URL-кодированный (`/` как `%2F`). Письма идут в порядке прихода (UID: у письма он не меняется, в отличие от даты, которую пишет отправитель): `order=newest` (по умолчанию) или `oldest`; сортировки по теме и отправителю нет. `limit` — 1…100 (50 по умолчанию). Ответ: `items` (id, отправитель, первые получатели, тема, дата, флаги `seen`/`flagged`/`answered`/`draft`, `hasAttachments`, метки — keywords без системных `$…`/`\…`, размер), `total` и `next`.

Курсор `next` — `uidValidity.uid` последнего письма страницы; его передают как `after`. Позиция по UID, а не номер страницы, поэтому новая почта страницы не сдвигает, а удалённое письмо (в том числе то, на котором остановился курсор) ничего не ломает и не повторяет. Сервер считает, сколько писем лежит до курсора (один поиск `ESEARCH COUNT`, без выкачивания всех UID), и берёт диапазон порядковых номеров: страница стоит столько же в папке на 50 000 писем, сколько в папке на 50. Курсор другой версии папки (`uidValidity` не совпал) — `409 uid_validity_changed`; несуществующая папка и папка-контейнер — `404 not_found` (имя папки в ответ не попадает); неверные `limit`, `after`, `order` — `400 bad_request`. Фильтры — VIN-044.

Превью (`preview`, одна строка до 200 символов) — по умолчанию в каждой строке; `preview=false` отключает его (для компактной плотности: серверу не приходится заглядывать в письма). Источник — расширение PREVIEW сервера; если его нет, MailKit сам скачивает начало письма (около 512 байт `text/plain`, до 16 КБ `text/html`; при двух вариантах берётся текстовый), декодирует кодировку и transfer-encoding (quoted-printable, base64, koi8-r, windows-1251…) и убирает разметку. В любом случае текст проходит `PreviewText.Normalize`: пробельные последовательности и переводы строк сводятся к одному пробелу, управляющие и невидимые символы (нулевой ширины, переопределения направления) удаляются, длина обрезается до 200 символов без разрыва суррогатных пар. Превью — недоверенный текст: клиент выводит его только как текст. Оба пути проверены на настоящем Dovecot на фикстурах (UTF-8 QP, base64, koi8-r, cp1251, только HTML, без тела).

Фильтр (`filter=all|unread|flagged`, по умолчанию `all`). Без фильтра страница — диапазон порядковых номеров (см. выше). С фильтром сервер выполняет один SEARCH (`UNSEEN` или `FLAGGED`) и возвращает только UID; страница вырезается из них по UID курсора (`<`/`>` в зависимости от порядка), и только её письма запрашиваются через FETCH. Положение — всегда UID, поэтому прочитанное, удалённое или новое письмо между страницами ничего не сдвигает и не повторяет. `total` при фильтре — число подходящих писем. Неизвестное значение — 400.

## Разбор письма

`IMessageParser` (Core) / `MimeMessageParser` (Mail, MimeKit) разбирает сырое письмо в `ParsedMessage`: тема, отправитель, получатели (все, группы раскрыты), дата, Message-ID, текстовое и HTML-тело, вложения, inline-части и значения заголовков Authentication-Results (для проверки отправителя, VIN-062). Письмо — недоверенный ввод, поэтому разбор ограничен и не бросает исключений на «битых» письмах: пустой ввод или не-письмо дают пустое сообщение; глубина дерева частей не больше 32, частей не больше 2000, остальное игнорируется. HTML-тело **сырое**: показывать его можно только после санитайзера (VIN-056).

Правила: тело берёт MimeKit (`multipart/alternative`, `related`, `mixed`); часть, из которой взято тело, во вложения не попадает. Часть с Content-ID без `Content-Disposition: attachment` — inline-часть (на неё ссылается `cid:`), всё остальное, что не тело, — вложение (в том числе часть, у которой имя только в Content-Type, и часть без имени). Вложенное письмо (`message/rfc822`) — одно вложение, его содержимое с основным не смешивается. Размер — после декодирования. Адрес части (`PartId`) — номера частей вниз по дереву, как номер секции IMAP (`1.2.1`): по нему скачивание (VIN-061) и cid-изображения (VIN-060) найдут часть. Имя файла проходит `AttachmentFileName.Sanitize`: берётся последний сегмент после `/` или `\` (`../../setup.exe` → `setup.exe`), удаляются управляющие, невидимые символы и переопределения направления, специальные символы заменяются на `_`, зарезервированные имена Windows получают префикс, длина не больше 150 с сохранением расширения; если ничего не осталось — имя по месту (`attachment-1.2`). Кодировки (VIN-055). Устаревшие кодировки (koi8-r, windows-1251, iso-8859-*, ibm866, shift_jis, gb2312, euc-kr…) в .NET отдаёт `CodePagesEncodingProvider`; без него MimeKit не декодирует их ни в заголовках, ни в теле. Провайдер регистрируется один раз при первом обращении к почтовому коду (`LegacyCharsets.Ensure()` в статических конструкторах `ImapMailSession` и `MimeMessageParser`), поэтому он есть и у списка писем, и у превью, и у разбора. Тело с кодировкой `us-ascii` или без кодировки, в котором есть байты выше 0x7F, читается как UTF-8, если байты — корректный UTF-8, иначе как windows-1252, а не превращается в «?»; для заголовков без кодирования решает MimeKit. Имя файла берётся из `Content-Disposition: filename`, при его отсутствии из `Content-Type: name`; поддержаны RFC 2231 (`filename*=`, части `*0*`, `*1*`, любые кодировки) и закодированные слова RFC 2047 (B и Q) в имени. Тесты — `CharsetTests` (байты собраны вручную для 25+ кодировок, трёх способов передачи, тем, имён, «грязного» base64 и quoted-printable).

Ожидаемый результат для каждой фикстуры задан в `tests/fixtures/manifest.json` и проверяется тестом `MimeMessageParserTests`.

## Настройки пользователя

Плотность списка, язык, цвета меток, доверенные отправители картинок (позже подписи и др.) хранятся по ящику: решение — [ADR-0004](adr/0004-user-settings-storage.md). `IUserSettingsStore` (Core): `GetAsync`, атомарный `UpdateAsync(mailbox, change)`, `DeleteAsync`; модель `UserSettings` сама проверяет пределы (`IsValid`: язык — короткий тег, до 200 цветов меток, имена и цвета — текст до 64 символов без управляющих). Реализация — `FileUserSettingsStore`: JSON на ящик в `Settings:Path`, имя файла — SHA-256 адреса в нижнем регистре; запись через временный файл и замену, изменения одного ящика сериализованы; поврежденный или больше 256 КиБ файл откладывается как `*.damaged-<время>`, пользователь получает значения по умолчанию. API: `GET /api/v1/settings` и `PATCH /api/v1/settings` (меняется только то, что передано: `density` = `comfortable`/`compact`, `language` — тег, пустая строка возвращает «как в браузере», `labelColors` — заменяет все цвета, `trustImagesFrom` / `untrustImagesFrom` — добавляют адрес в список доверенных отправителей картинок и убирают его, не трогая остальное; неверное значение — 400 `bad_request`, ничего не сохраняется). Только один экземпляр (или общий каталог); несколько экземпляров — будущий `ImapMetadata`. Каталог должен быть на постоянном хранилище (в образе — `/data/settings`).

## Открытие письма

`GET /api/v1/messages/{id}` (`MessageEndpoints`): `IMailSession.GetMessageAsync` открывает папку **только для чтения** и забирает письмо целиком через `BODY.PEEK[]` — просмотр не помечает письмо прочитанным (это отдельное действие, VIN-066). Письмо больше 32 МБ (`MessageLimits.MaxViewableBytes`) не скачивается: сначала проверяется размер из `FETCH`, затем и фактическое число байт; ответ `413 payload_too_large`. Нет письма — `404 not_found`, другая версия папки — `409 uid_validity_changed`, битый идентификатор — `400`. Дальше `IMessageParser` разбирает письмо (VIN-054), и тело выбирается так: очищенный HTML (`bodyFormat = html`); если HTML нет, он пуст после очистки или отклонён как слишком глубокий — простой текст, превращённый в HTML (`PlainTextHtml`: экранирование, сохранённые переносы, `http(s)://`, `www.` и адреса почты как ссылки, строки `>` как вложенные цитаты) и **тоже прошедший через санитайзер**, чтобы одно правило покрывало всё, что уходит с сервера (`text`); иначе `empty`. Ответ содержит заголовки, всех получателей, флаги, метки, `body`, `blockedExternalResources`, `truncated`, список вложений (`partId`, имя, тип, размер) и отдаётся с `Cache-Control: private, no-store`. Картинки письма (`cid:`) встраиваются в тело как `data:image` (см. ниже), необработанные заголовки Authentication-Results наружу не уходят (наружу идёт только итог проверки отправителя, см. ниже). Содержимое писем в логи и ошибки не попадает.

### Картинки внутри письма (`cid:`)

Страница письма живёт в `iframe` с `sandbox` без `allow-same-origin`: у неё нет своего origin, и запрос к `/api/...` ушёл бы без cookie сессии (`SameSite=Strict`), поэтому отдельный адрес для картинок не работает. Вместо этого сервер **встраивает** картинки в тело: `InlineImageResolver` отвечает санитайзеру на каждый `cid:` и возвращает `data:image/…;base64,…`. Правила: (1) тип определяется по первым байтам (`InlineImage.Sniff`: PNG, JPEG, GIF, WebP), а не по заявленному — часть, названная `image/png`, но содержащая HTML, не картинка; (2) SVG никогда (в нём бывают скрипты); (3) одна картинка до 1 МБ (`MaxInlineImageBytes`), на тело вместе до 8 МБ (`MaxInlineImagesTotalBytes`), одна и та же картинка дважды считается один раз; (4) Content-ID сопоставляется без учёта регистра, с угловыми скобками и `%`-кодированием (`cid:logo%40example.org`); (5) неизвестный `cid:` или картинка, не прошедшая проверку, — адрес удаляется. Парсер хранит байты inline-части только если она не больше 1 МБ. Такой адрес санитайзер не перепроверяет: его строит само приложение из проверенных байтов. В список вложений inline-картинки не попадают.

### Защита от тяжёлых писем

Письмо недоверенное и может быть огромным или построенным так, чтобы занять сервер. Ограничения, от внешних к внутренним:

- **Размер письма.** `Imap:MaxViewableMessageBytes` (по умолчанию 32 МБ; диапазон 1–512 МБ; задаётся в `appsettings`/`VINETTE_Imap__MaxViewableMessageBytes`). Письмо разбирается в памяти, поэтому большее не скачивается: размер берётся из `FETCH` до загрузки, а при загрузке считается и фактическое число байт (сервер мог занизить). Ответ — `413 payload_too_large` для письма и для скачивания вложения («Письмо слишком большое, чтобы показать его здесь»). Обычный почтовый сервер не принимает письма больше 10–50 МБ, так что лимит — страховка.
- **Дерево частей:** глубина ≤ 32, частей ≤ 2000 (парсер); размер вложения при разборе только считается потоком (в память не копируется), а inline-картинка хранится, если она ≤ 1 МБ.
- **Тело: сначала начало.** HTML или текст длиннее `MessageLimits.DefaultBodyChars` (250 000 знаков) очищаются и отдаются **усечёнными**: `truncated: true`, `canShowFull: true`. «Показать целиком» — тот же запрос с `?full=true` (до `FullBodyChars`, 1 000 000 знаков — больше не показывается никогда: `canShowFull` тогда `false`). Интерфейс: «Письмо очень длинное: показано только его начало.» и кнопка «Показать целиком» (`ReadingPane`); пока приходит остальное, начало остаётся на экране, а кнопка занята.
- **Санитайзер:** вход ограничен длиной выше; вложенность элементов глубже 200 отклоняется заранее (глубокое дерево может исчерпать стек, а это не перехватить) — показывается текстовая версия; очистка идёт в рабочем потоке и ограничена **5 секундами** (`MessageLimits.SanitizeTimeout`): если разметка держит очиститель дольше, она считается отклонённой (поток заканчивает сам: вход ограничен). `PlainTextHtml` — линейное время.
- **«HTML-бомбы»** (`HtmlBombTests`, 17 видов: 150 000 вложенных `div`, 60 000 соседних `span`, один атрибут в 240 000 знаков, 30 000 атрибутов у тега, 8 000 блоков `<style>`, 30 000 перекрёстно вложенных `<b><i>`, «adoption agency» с таблицами, сущности, комментарии, ссылки, 20 000 селекторов, незакрытые теги и др.): каждая очищается или отклоняется быстрее 10 с (на практике худшая — около 1,3 с).

### Внешние изображения (`?images=true`)

Письмо часто ссылается на картинки в сети. Если браузер пользователя загрузит их сам, отправитель узнает, что письмо открыли, когда и с какого адреса. Поэтому по умолчанию они скрыты, а по просьбе пользователя **их скачивает бэкенд и кладёт в тело как `data:image`**. Отдельного прокси-адреса нет: рамка письма не имеет origin, cookie сессии (`SameSite=Strict`) в её запросах не уходит, а CSP остаётся `img-src data:` (VIN-059, решение владельца).

Поток: `GET /messages/{id}` очищает тело и возвращает `canShowImages` (есть что показать, не запрошено, функция включена) и `blockedExternalResources`. `GET /messages/{id}?images=true`: санитайзер собирает адреса картинок (`SanitizedHtml.ExternalImages`, без повторов, не больше 30; `//host` считается как `https://host`), `IExternalImageFetcher` скачивает их, тело очищается заново с резолвером «адрес → data URI» (`Sanitize(…, resolveExternalImage)`); то, что скачать не удалось, остаётся скрытым (`imagesShown` — сколько встроено). Резолверу тоже не верят: санитайзер пропускает только `data:image/png|jpeg|gif|webp;base64`. Фоны, `srcset`, стили, ссылки остаются заблокированными — подставляются только `img src`.

Защита от SSRF (`Mail/Images/`, у каждого пункта тест в `ExternalImageFetcherTests`/`AddressPolicyTests`):

- Только `http`/`https`, порты `ExternalImages:AllowedPorts` (по умолчанию 80 и 443), без логина и пароля в адресе.
- **Только публичные адреса** (`AddressPolicy`): закрыты loopback, частные (10/8, 172.16/12, 192.168/16), link-local и метаданные облака (169.254.0.0/16), CGNAT, документационные, multicast, зарезервированные; IPv6 — только 2000::/3, а IPv4-в-IPv6 (mapped, NAT64, 6to4, совместимые) судятся по вложенному IPv4, Teredo и ORCHID закрыты. Адрес, записанный числом (`2130706433`, `0x7f000001`, `127.1`), разбирается так же, как это делает сеть, и проверяется как любой другой.
- **Имя разрешается один раз — в момент соединения** (`ConnectCallback`), и соединение идёт на проверенный адрес: второго запроса к DNS, который мог бы ответить иначе (DNS rebinding), нет. Если среди ответов есть и частные, и публичные, используются только публичные.
- Редиректы идут вручную (до `MaxRedirects`, 3), и каждая цель проверяется заново целиком.
- Без cookie, `Authorization`, `Referer`, прокси и сжатия; обычный `User-Agent`, не называющий Vinette.
- Лимиты: 2 МБ на картинку (по `Content-Length` и по факту при чтении), 10 МБ и 30 картинок на письмо (что не влезло — выбрасывается целиком), 5 с на картинку с редиректами, 10 с на все, шесть параллельно; отмена запроса прерывает всё.
- Ответ судится по первым байтам (`InlineImage.Sniff`): PNG, JPEG, GIF, WebP; SVG и HTML под видом картинки отбрасываются, что бы ни написал сервер в `Content-Type`.
- В журнал попадает только число («скачано 3 из 5»): адреса картинок и пользователя в логах нет. Ответ пользователю не различает причины («не удалось загрузить»), чтобы нельзя было сканировать внутреннюю сеть по ошибкам.

Включается и настраивается секцией `ExternalImages` (`Enabled` — выключить функцию целиком, остальное — лимиты выше). `AllowPrivateAddresses` — только для тестов и машины разработчика: на настоящем сервере письмо смогло бы читать страницы внутренней сети.

### Горячие клавиши (VIN-077)

`features/mailbox/shortcuts.ts`: `shortcutOf(event)` — чистая функция (клавиша → `next | previous | open | archive | delete | search | compose | help` или `null`), `useShortcuts(handlers)` — один обработчик `keydown` на документе (всегда вызывается последняя версия обработчиков; клавиша без обработчика остаётся браузеру, с обработчиком — `preventDefault`). Правила: клавиши читаются по положению на клавиатуре (`event.code`: `KeyJ`, `KeyK`, `KeyE`, `KeyC`, `Slash`), поэтому работают и в русской раскладке; `#` и `?` — ещё и по напечатанному знаку (`Shift+3`, `Shift+/`); с Ctrl/Alt/⌘, при `isComposing` (IME), при открытом диалоге (`[role=dialog]`) и в текстовых полях (`input` любого текстового типа, `textarea`, `select`, `contenteditable`) ничего не происходит; чекбокс, радиокнопка и кнопка — **не** поле ввода (иначе после щелчка по чекбоксу строки клавиши молчали бы); `Enter` на ссылке или кнопке остаётся за ней.

Подключено в `MessageListPane`: **курсор** — строка списка с кольцом акцентного цвета (`data-cursor`), `j`/`k` двигают его (с прокруткой виртуального списка к строке, `scrollToKey`) и не выходят за концы; у открытого письма курсор по умолчанию на нём, и `j`/`k` сразу открывают соседнее; `Enter` открывает строку под курсором. `e` и `#` применяются к выбранным письмам → иначе к открытому / строке под курсором (`useMessageBatch`: оптимистично, с «Отменить»); архив не применяется в архивной папке, удаление — в корзине. `/` фокусирует поиск (на телефоне сначала открывает его), `c` — к написанию письма, `?` — диалог «Горячие клавиши» (`ShortcutsDialog`): **единственное место, где клавиши объяснены**, подсказок на основном экране нет (решение владельца; кнопка в меню аккаунта — позже, VIN-120). Курсор привязан к папке и фильтру. `r` (ответить) не включён: он появится вместе с редактором (VIN-102) — тогда же его строка в диалоге.

`Dialog` (`shared/ui`, есть в `/dev/ui`): портал в `body`, `role="dialog"` `aria-modal`, фокус внутрь и по кругу (Tab/Shift+Tab), Esc, крестик и щелчок по затемнению закрывают, фокус возвращается на прежний элемент.

### Кнопки действий над открытым письмом (VIN-074)

`ReaderActionBar` в `ReadingPane`: «В архив», «В спам», «Удалить» (перенос **в корзину**, обратимо; из самой корзины «Удалить навсегда» — VIN-079 с подтверждением), флажок и «Ещё». Панель только сообщает, что просят (`onAction('archive' | 'spam' | 'trash' | 'unread')`); что делать дальше решает экран: `MailboxPage` отправляет `POST /messages/batch` с одним письмом (`useMessageBatch`, тот же код, что у мультивыбора), после успеха возвращает к списку с теми же параметрами (`?filter=`), при ошибке остаётся на письме и пишет понятными словами (`errors.no_target_folder` — «нет подходящей папки (архив, спам или корзина)»). Папка письма берётся из списка папок: действие, которое оставило бы письмо на месте, не показывается (архив в архиве, спам в спаме, удалить в корзине). Пока действие идёт, кнопки ждут.

**Оптимистичные обновления и тосты (VIN-075).** `useMessageBatch` (`features/mailbox/batch.ts`) показывает результат до ответа сервера: `onMutate` отменяет текущие загрузки, делает снимок кэша (списки `['messages']`, открытые письма `['message']`, папки) и применяет действие (`applyBatch`): переносимое письмо уходит из **всех** кэшированных списков, у папки-источника уменьшаются «всего» и «непрочитанных» (по строкам, которые видны в кэше), у папки назначения (по роли: архив, спам, корзина) — растут; «прочитано/непрочитано» меняет метку строк и открытого письма и счётчик непрочитанных только по тем письмам, у которых состояние действительно меняется; флажок меняет только флажок. Папка письма берётся из его id (`folderOfId`). Если сервер отказал — `restore` возвращает снимок, а **тост-ошибка** (`shared/toast`, `describeApiError`) объясняет, что случилось, человеческими словами; список выделенных писем тоже возвращается. Действия идут по очереди (`scope`), чтобы откат одного не затёр следующее; после любого исхода (`onSettled`) списки и счётчики перезапрашиваются, и экран сходится с сервером. Флажок одного письма (`useSetFlags`) делает то же самое с VIN-066.

`Toast` (`shared/ui`, есть в `/dev/ui`) — только вид; `ToastProvider` (`shared/toast`, в `app/providers.tsx`) показывает до трёх тостов внизу по центру (на телефоне выше кнопки «Написать»), убирает их через 6 с (ошибка — 8 с), время стоит, пока на тосте курсор или фокус; `useToast().show({ message, tone, action })`. **Отмена (VIN-076).** После успешного переноса (архив, спам, корзина — из панели чтения и из мультивыбора) `useMessageBatch` показывает тост «Письмо перенесено в корзину» (формы по числу: «2 письма перенесены…», `toast.moved.<действие>`) с кнопкой «Отменить». Отмена — ещё один перенос: идентификаторы писем **в новой папке** берутся из ответа (`moved[].id`), прежняя папка — из исходных идентификаторов (`folderOfId`), запрос — `POST /messages/batch` с `action: "move"` и `to`. После неё списки и счётчики перезапрашиваются, письма появляются на прежнем месте (под новыми UID: IMAP не умеет вернуть UID). Если сервер не сообщил новые идентификаторы (нет UIDPLUS), кнопки нет — тост только сообщает о переносе; если сама отмена не удалась, тост-ошибка говорит, где искать письмо. Отмены у «прочитано/непрочитано» и флажка нет (они обратимы тем же действием). Тост живёт 6 с (кнопка доступна всё это время; пауза при наведении и фокусе).

«Ещё» (`MoreMenu`) — панель под кнопкой (закрывается Escape, щелчком снаружи и выбором): «Отметить непрочитанным» (после него — к списку, иначе письмо тут же снова прочиталось бы) и на телефоне, где в панели нет иконок действий, — «В архив», «В спам», «Удалить», «Флажок». Остальное меню — VIN-079. Оптимистичное обновление и отмена — VIN-075/076.

### Мультивыбор и пакетные действия (VIN-073)

`POST /api/v1/messages/batch` с `{ "ids": [...], "action": "...", "to": "..." }`: `archive`, `spam`, `trash` (папка по роли, как у одиночных действий), `move` (с `to`), `read`, `unread`, `flag`, `unflag`. **Лимит пачки — 100 писем** (`MessageBatch.MaxMessages`, решение владельца): все из одной папки с одним `UIDVALIDITY`, без повторов, иначе 400 `bad_request`. Пачка — одна IMAP-команда на набор UID (`UID MOVE`/`COPY`+`STORE`+`UID EXPUNGE`, `UID STORE`), поэтому по времени она как одно письмо. Письма, которых уже нет, пропускаются (одним `UID SEARCH` до действия) — `changed` в ответе тогда меньше запрошенного; для переноса ответ даёт `moved: [{ from, id }]` (новые id, если сервер их сообщает) — для отмены (VIN-076).

Фронтенд (оптимистичное обновление — VIN-075, ниже): выбор — чистые функции `features/mailbox/selection.ts` (`toggle`, `extend` для Shift-диапазона в порядке списка, `selectAll` — загруженные письма, не больше 100, `keepListed` — выбор забывает исчезнувшие строки); состояние в `MessageListPane` привязано к папке и фильтру (другой список начинается без выбора). `SelectionBar` заменяет строку шапки; Если открытое письмо ушло в другую папку, адрес возвращается к списку.

### Метки (VIN-072)

Метка — **IMAP keyword** на письме: её видят и другие почтовые программы, а письмо при переносе между папками её сохраняет. Что сервер хранить не умеет, лежит в настройках пользователя ([ADR-0004](adr/0004-user-settings-storage.md)): **список меток** (метка живёт и до того, как её назначили хоть одному письму; решение владельца) и **цвета** (`labelColors`, ключи палитры из DESIGN.md: `work`, `bills`, `personal`).

**Имя в keyword (`LabelName`, Core; решение владельца).** Keyword — простое ASCII-слово, без учёта регистра, не длиннее 50 знаков (`mail_max_keyword_length` Dovecot). Поэтому: простое имя (`Work`, `Bills-2026`: латинские буквы, цифры, `_ . -`, начинается с буквы) хранится **как есть** — другие клиенты читают его без перевода; любое другое (пробел, кириллица, эмодзи) — `vl-` + UTF-8 в **base32 нижнего регистра** (base64 не годится: сервер не различает регистр). Только Vinette читает такое имя обратно; в других клиентах оно выглядит как `vl-…`. Следствие лимита: закодированное имя — до ~14 русских букв, простое — до 50 знаков (длиннее — 400 `bad_request`). Имена без учёта регистра считаются одной меткой; `/`, `\` и управляющие знаки запрещены. Системные флаги (`\Seen`, `$…`) метками не считаются.

API (все маршруты требуют сессии; изменяющие — и CSRF-токена):

| Запрос | Что делает |
| --- | --- |
| `GET /labels` | метки ящика: список пользователя + то, что **сейчас** висит на письмах во «Входящих» (так находятся метки, поставленные другими программами) |
| `POST /labels` `{name, color?}` | создать метку (без писем); имя занято — 409 `conflict` |
| `PATCH /labels/{name}` `{name?, color?}` | переименовать (метка меняется **на каждом письме каждой папки**: `SEARCH KEYWORD` + `STORE`) и/или сменить цвет (пустая строка снимает); новое имя занято — 409 |
| `DELETE /labels/{name}` | снять метку со всех писем и забыть её; сами письма не затрагиваются |
| `GET /labels/{name}/messages?limit&preview` | письма с меткой **из всех папок, кроме Корзины и Спама**, новейшие первыми, по дате: `SEARCH KEYWORD` в каждой папке (`IMailSession.ListLabeledMessagesAsync`), у каждой папки берутся `limit` новейших UID, дальше слияние и обрезка до `limit` (1…100, по умолчанию 50). Страница **одна**: `next` всегда пуст, `total` — сколько писем с меткой всего (может быть больше `items`); у каждого письма свой id со своей папкой. Неизвестная метка — пустой список, неверное имя или `limit` — 400 |
| `PATCH /messages/{id}/labels` `{add?, remove?}` | поставить и снять метки на письме (не больше 20 за раз; новое имя попадает в список меток); отвечает метками письма |

**Метки в интерфейсе (VIN-078, решения владельца; `features/labels`).** Сайдбар: «+» открывает поле имени (Enter — создать), у строки метки меню «⋯» (цвет из трёх цветов палитры, «Переименовать», «Удалить» с подтверждением); щелчок открывает `/mail/@label/<имя>` — тот же `MailboxPage` и `MessageListPane` в режиме метки (`labelName`): данные из `useLabelMessages` (ключ начинается с `messages`, поэтому действия над списком — перенос, флажки — достают и его), без чипов-фильтров и без мультивыбора (письма лежат в разных папках, а пакетное действие — для одной). `@label` не может совпасть с папкой: папка в адресе всегда закодирована (`%40label`). Сервер отдаёт SPA по любому `/mail/…`. Назначение меток — панель «Метки» (`MessageLabelsMenu`): в панели действий письма и в панели мультивыбора; чекбокс частично заполнен, если метка не у всех выбранных писем; поле внизу создаёт метку и вешает её. `useSetMessageLabels` меняет письма **по очереди** (сервер меняет метки одного письма за запрос) и показывает результат сразу (кэш списков и открытых писем), при отказе возвращает снимок и показывает тост. Клавиша `l` — VIN-137.

Метки письма видны в списке и в самом письме (`labels` в ответах; `LabelsOf` декодирует имена), цвет берётся из настроек (`labelColor(label, labelColors)` на фронтенде; метка без выбранного цвета получает цвет по имени, как раньше).

Особенности: сервер **никогда не забывает** keyword в `PERMANENTFLAGS` (удалённая или переименованная метка вернулась бы), поэтому `GetLabelsAsync` берёт только те keywords, которые найдены поиском на письмах во «Входящих» (`SEARCH KEYWORD` на каждое слово; папка открывается на запись, в режиме `EXAMINE` сервер не перечисляет флаги). Метки только на письмах в других папках в этот список попадают, лишь если пользователь поставил их в Vinette (они в его списке). Смена регистра в имени (`work` → `Work`) меняет только подпись в списке: на сервере keyword один. Переименование идёт сначала на сервере, потом в настройках: при сбое настройки остаются с прежним именем.

### Доверенные отправители картинок

«Всегда показывать картинки от этого отправителя» (VIN-068, решения владельца: точный адрес, только для подтверждённых, управление в самом письме). Список адресов хранится в настройках (`UserSettings.TrustedImageSenders`: нижний регистр, без повторов, отсортирован, до 500 адресов по 254 знака; `GET`/`PATCH /settings`).

- Адрес сравнивается **точно** (регистр не важен); домен целиком не доверяется.
- **Доверие само по себе картинки не включает.** Сервер загружает их без вопросов, только если проверка отправителя (`SenderVerifier`) даёт `verified`; строка From подделывается легко, и без этого мошенник, назвавшись доверенным адресом, получил бы автозагрузку (то есть отслеживание). Если проверка не подтверждена, картинки скрыты и есть обычная кнопка «Показать». Это покрыто тестом `TrustedImageSendersApiTests`.
- Письмо отвечает полями `hasExternalImages` (в теле есть картинки из сети), `imagesTrusted` (адрес отправителя в списке), `canShowImages`, `imagesShown`.
- Интерфейс (`ImageTrust` в `ReadingPane`): под сообщением о скрытых картинках — «Отправитель подтверждён. Показывать его картинки сразу, без вопросов?» + «Всегда показывать»; если адрес уже в списке — «Картинки от … показываются сразу.» + «Не показывать сразу». Предложение есть только у подтверждённого отправителя (иначе выбор ничего не изменил бы); отозвать доверие можно всегда. После выбора открытое письмо загружается заново. Отдельного экрана со списком пока нет: он появится вместе с экраном настроек.

### Мобильный просмотр

На телефоне (< 768 px) письмо занимает весь экран; список и письмо лежат в одной ячейке сетки (`AppShell`), письмо поверх. **Список не убирается из страницы**, а только становится невидимым (`visibility: hidden`: он остаётся в раскладке, не доступен ни клавиатуре, ни скринридеру) — поэтому всё, что в нём загружено, и положение прокрутки сохраняются сами; `display: none` и размонтирование сбрасывали бы прокрутку в 0. Раньше для списка и письма было два маршрута и экран пересобирался при открытии письма; теперь один маршрут `/mail/:folder/:messageId?`. Кнопка «Назад» (`ReaderActionBar`, первая в панели; страница передаёт `onBack` только на телефоне) идёт по адресу списка с сохранением фильтра; системная «Назад» браузера делает то же, так как открытие письма — обычный переход. Фокус: при открытии письма он переходит на область чтения (`<main tabIndex=-1>`), при возврате — на строку, которая была открыта (адрес её больше не называет, поэтому строка запоминается при открытии). Цели нажатия кнопок панели не меньше 44 px (`max-md:size-11`, `max-md:h-11`). Проверено в настоящем Chromium (390 px): прокрутка списка 700 px, открытие строки, возврат — позиция та же, фокус на строке, браузерная «Назад» тоже возвращает позицию.

### Прочитано и флажок

`PATCH /api/v1/messages/{id}/flags` с телом `{ "seen": true|false, "flagged": true|false }` (меняется только то, что передано; пустое тело — 400): `IMailSession.UpdateFlagsAsync` открывает папку на запись, проверяет, что письмо есть (иначе 404) и версию папки (иначе 409), выполняет `STORE +/-FLAGS` для `\Seen` и `\Flagged` и отвечает флагами письма после изменения (`seen`, `flagged`, `answered`, `draft`). Повтор того же изменения безвреден, поэтому запрос можно повторять после переподключения; другие флаги и метки не трогаются. Нужны сессия и CSRF-токен.

На фронтенде `useSetFlags` (`features/message/flags.ts`): **оптимистично** меняет письмо в кэше и его строку во всех загруженных страницах всех списков; ответ сервера уточняет, а при ошибке прежнее состояние возвращается из снимка, сделанного до изменения. Изменения одного письма идут по очереди (`scope`). После завершения запрашиваются заново только счётчики папок (`['folders']`), а не списки: строка не должна выпрыгивать из-под читателя оттого, что перестала быть «непрочитанной». `ReadingPane` при открытии непрочитанного письма сам отмечает его прочитанным — один раз на письмо; если сервер отказал, отметка возвращается и повторно не навязывается, пользователю ничего не говорится. Кнопка «Флажок» включена: нажатие меняет её сразу; при ошибке она возвращается и появляется понятное сообщение «Не удалось сохранить отметку…» (пропадает после следующего удачного изменения). «Пометить непрочитанным» — позже (VIN-079).

**Адреса писем и перезагрузка.** Идентификатор письма содержит точки (`SU5CT1g.1731000000.42`), а запасной маршрут приложения по умолчанию (`{*path:nonfile}`) считает адрес с «расширением» в последнем сегменте файлом и отвечает 404 — ссылка на письмо не открывалась после перезагрузки страницы и из закладки. Добавлен второй запасной маршрут `/mail/{*path}`: всё под `/mail` открывает приложение. Остальные «файлоподобные» адреса по-прежнему не отдают приложение, `/api`, `/hubs`, `/branding`, `/metrics` — тоже.

### Действия над письмами (API)

VIN-071; интерфейс — VIN-074 и далее. Все маршруты требуют сессии и CSRF-токена (изменяющие запросы).

| Запрос | Что делает |
| --- | --- |
| `POST /messages/{id}/archive` | перенос в папку-архив ящика |
| `POST /messages/{id}/spam` | перенос в папку спама |
| `POST /messages/{id}/trash` | перенос в корзину |
| `POST /messages/{id}/move` с `{ "to": "<path папки>" }` | перенос в любую папку (в том числе обратно во «Входящие» — так делается отмена) |
| `DELETE /messages/{id}` | **удалить навсегда**; разрешено только для письма, лежащего в корзине (иначе 409 `not_in_trash`) |
| `POST /messages/batch` `{action: "delete"}` | то же для выбранных писем (до 100, одна папка): только в корзине, иначе 409 `not_in_trash`; `changed` — сколько удалено (`IMailSession.DeleteMessagesPermanentlyAsync`: `\Deleted` + `UID EXPUNGE` набором UID) |
| `POST /folders/{folder}/empty` | **очистить** корзину или спам: все письма папки удаляются навсегда (`EmptyFolderAsync`), ответ `{deleted}`; любая другая папка — 409 `not_in_trash`. Роль папки та же, что в сайдбаре (`FolderRoleGuesser`) |

Ответ переноса — `{ "id": "<id письма в новой папке>", "folder": "<path>" }`. `id` отсутствует, если сервер не сообщает новый UID (нет UIDPLUS): тогда письмо ищут в папке. Старый идентификатор после переноса недействителен (`404 not_found`): письмо с тем же UID в другой папке — это другое письмо. Идентификатор нужен клиенту, чтобы вернуть письмо на место (VIN-076).

Папка для архива, спама и корзины берётся по роли, **теми же правилами, что в боковой панели** (`SPECIAL-USE` сервера, затем `FolderRoleGuesser` по названию). Если такой папки у ящика нет — 409 `no_target_folder` (приложение папку само не создаёт: решение владельца потом; интерфейс объяснит, что делать). Перенос письма в папку, где оно уже лежит, — 400 `bad_request`; неизвестная папка — 404 `not_found` (имя папки в ответ и в лог не попадает).

IMAP: основной путь — `MOVE` (RFC 6851); если сервера нет расширения — запасной: `COPY`, затем метка `\Deleted` и `UID EXPUNGE` **только этого письма** (UIDPLUS; чужие пометки `\Deleted` у соседних писем не затрагиваются — проверено тестом). Сервер без UIDPLUS отдельно не проверялся: MailKit для него использует собственный обходной путь. Копия идёт первой: при сбое письмо остаётся на месте и не пропадает. Оба пути проверяются интеграционными тестами на настоящем Dovecot (`MessageMoveIntegrationTests`; запасной путь включается в тесте `ImapMailSessionFactory.MoveExtension = false`), включая случай, когда другой клиент пометил соседнее письмо удалённым.

«Удалить» в интерфейсе будет переносом в корзину (обратимо, VIN-076), «Удалить навсегда» — только из корзины и с подтверждением (VIN-079).

### Скачивание вложений

`GET /api/v1/messages/{id}/attachments/{partId}` (`MessageEndpoints.DownloadAsync`): `partId` — адрес вложения из ответа письма (`1.2.1`; формат проверяется, иначе 400). Сервер читает письмо (те же коды ошибок: 404, 409, 413), `IMessageParser.ExtractAttachmentAsync` проходит дерево тем же обходом, что и список вложений, поэтому отдаётся только то, что в списке: тело, inline-картинка и контейнер — 404; имя и тип те же, что в списке. Ответ — всегда скачивание: `Content-Disposition: attachment` с безопасным именем (`filename` и `filename*` для кириллицы), даже если письмо объявило часть `inline`; `X-Content-Type-Options: nosniff`; `Content-Security-Policy: default-src 'none'; sandbox` на случай, если файл когда-нибудь откроют как страницу; `Cache-Control: private, no-store`; `Referrer-Policy: no-referrer`. Тип ответа — `AttachmentContentType.ForDownload`: короткий список безвредных типов (PDF, архивы, офисные форматы, растровые картинки, аудио и видео, `text/plain`, `text/csv`, `message/rfc822`), всё остальное — `application/octet-stream`. HTML, XHTML, SVG, XML, JavaScript, CSS и неправильно записанные типы никогда не уходят со своим типом. Содержимое файла не меняется. Прикреплённое письмо отдаётся как `.eml` (`message/rfc822`). Для скачивания достаточно обычной ссылки (`<a href>`): cookie `SameSite=Strict` при переходе по ссылке со страницы приложения передаётся.

### Проверка отправителя

`SenderVerifier` (Core) превращает заголовки `Authentication-Results` (RFC 8601) в итог `verified` / `suspicious` / `unknown` — поле `sender` ответа письма (`verdict`, `domain` из адреса From). Заголовок — слова того, кто его написал, а отправитель может приписать свой, поэтому правила такие (решение владельца, 2026-11-12):

- **«Подтверждён» — только по самому верхнему заголовку, и только если имя сервера в нём (`authserv-id`) в списке доверенных** (`SenderCheck:TrustedAuthservIds`; пусто = адрес почтового сервера `Imap:Host`). Свой заголовок почтовый сервер ставит первым и удаляет подделки под своё имя; всё, что ниже или с чужим именем, для «подтверждён» не считается. Если имя сервера в заголовке не совпадает с настроенным (`myhostname` отличается от `Imap:Host`), плашка не появится — укажите имя в `SenderCheck:TrustedAuthservIds`.
- **«Подозрительно» — по любому заголовку** (подделанный провал вредит только самому письму): `dmarc=fail`; а если DMARC нет — `spf=fail` или `dkim=fail` без единого прохождения. `dmarc=fail` с политикой `none` (`p=none`, `policy=none` в комментарии) тревоги не вызывает — так выглядят рассылки.
- **Прохождение:** `dmarc=pass` (и `header.from` совпадает с доменом From), а без DMARC — `dkim=pass` с `header.d` или `spf=pass` с доменом `smtp.mailfrom`, согласованными с From (тот же домен или поддомен; как и в DMARC, одного согласованного прохождения достаточно). Иначе — `unknown`, ничего не показываем.

Разбор устойчив к реальным форматам (OpenDKIM, OpenDMARC, Rspamd, Dovecot): комментарии в скобках, строки в кавычках, переносы, версия после имени, регистр; кривой, слишком длинный (> 16 КБ) или враждебный заголовок даёт `unknown` за линейное время. «Подтверждён» означает проверку домена в строке From, а не честность отправителя: домен-двойник тоже может пройти проверки.

## Квота

`GET /api/v1/quota` → `{ "storage": { "usedBytes", "limitBytes" } }` (GETQUOTAROOT по INBOX; IMAP отдаёт килобайты по 1024 байта, API — байты). Поле `storage` отсутствует, и интерфейс ничего не показывает, если у сервера нет расширения QUOTA (его не спрашивают), у ящика нет лимита на объём (только на число писем) или сервер отказал в запросе. Ошибки связи — как у остальных почтовых запросов (503).

## Сессии и учётные данные

- Пароль пользователя хранится только на сервере и только в зашифрованном виде (ASP.NET Core Data Protection).
- В браузере — httpOnly-cookie с непрозрачным идентификатором сессии; пароль и токены доступа в браузер не попадают.
- Время жизни сессии ограничено двумя параметрами: простой (`Session:IdleTimeout`) и абсолютный максимум (`Session:MaxLifetime`).
- Ключи Data Protection должны храниться персистентно (`DataProtection:KeysPath`), иначе после перезапуска все сессии теряются.

### Контракты входа (Vinette.Core)

- `IAuthenticator` проверяет учётные данные на почтовом сервере и возвращает исход (`Succeeded`, `InvalidCredentials`, `ServerUnavailable`); реализация на IMAP — в `Vinette.Mail`.
- Доступ к почте после входа идёт только через интерфейсы `Vinette.Core.Mail`: `IMailGateway` (выполнить команду от имени сессии; соединения, очередь команд и переподключение — внутри него), `IMailSession` (одно авторизованное соединение; операции с папками и письмами добавляют функции, которым они нужны) и `IMailSessionFactory` (открыть соединение; реализация на MailKit — в `Vinette.Mail`). Ошибки: `MailUnavailableException` (сервер недоступен) и `MailAccessRevokedException` (пароль больше не принимается — сессию надо завершить). `Vinette.Core` и `Vinette.Api` не ссылаются на MailKit/MimeKit; это проверяют `AuthenticationContractTests` и `ArchitectureTests`.
- `MailConnectionManager` (Vinette.Mail) — реализация `IMailGateway`: одно долгоживущее IMAP-соединение на веб-сессию, открывается первой командой (`ImapMailSessionFactory`: подключение, команда ID с `x-originating-ip`, LOGIN) и переиспользуется. Команды одной сессии идут строго друг за другом (на каждое соединение — свой семафор), разные сессии друг друга не ждут; отмена выводит ожидающую команду из очереди, а команду, прерванную на полпути, — вместе с соединением (состояние потока после обрыва неизвестно): следующая команда открывает чистое соединение. Порядок команд одной сессии — порядок поступления. Умершее соединение заменяется при следующем запросе. Выход (`POST /api/v1/auth/logout`) закрывает соединение после текущей команды. Отказ сервера принять пароль — `MailAccessRevokedException`, недоступность — `MailUnavailableException`. Переподключение: если соединение не открывается или рвётся посреди команды, менеджер пробует ещё 3 раза с растущей паузой (0,2 → 0,6 → 1,8 с, разброс ±20 %) и только потом отвечает `503 mail_unavailable`; команду повторяют, лишь если вызывающий код не запретил это (`safeToRepeat: false` для отправки, добавления и удаления). Если сервер не принимает сохранённый пароль (его сменили или отозвали доступ), повторов нет — лишние неверные пароли могли бы заблокировать ящик: `MailExceptionHandler` завершает веб-сессию на сервере, закрывает её почтовое соединение, стирает cookie и отвечает `401 session_revoked`. Освобождение ресурсов: `MailConnectionCleanupService` раз в полминуты (чаще, если `Imap:ConnectionIdleTimeout` меньше минуты) закрывает соединения, которыми не пользовались дольше `Imap:ConnectionIdleTimeout` (5 минут); следующий запрос пользователя открывает новое, выполняющаяся или ожидающая команда соединение удерживает. При остановке приложения менеджер (singleton, `IAsyncDisposable`) дожидается текущих команд и закрывает все соединения командой LOGOUT. Лимиты: место под соединение занимается при его открытии и освобождается при закрытии (выход, простой, обрыв, остановка). Потолки — `Imap:MaxConnectionsPerUser` (5 на ящик: сессии с нескольких устройств) и `Imap:MaxConnections` (200 всего); команда, которой нужно новое соединение, ждёт место до `Imap:ConnectionWaitTimeout` (10 с), затем `MailBusyException` → `503 mail_busy` с `Retry-After`. Существующие соединения лимит не затрагивает: уже открытая сессия продолжает работать.

- **Слежение за ящиком (VIN-081, [ADR-0006](adr/0006-mailbox-watching.md)).** `IMailboxWatcher.Subscribe(address, sessionId, credentials, onChange)` (Core) возвращает `IDisposable`; реализация `MailboxWatcher` (Mail) держит по одному соединению на ящик (`IMailSession.WatchInboxAsync`: IMAP IDLE на «Входящих»; без IDLE — NOOP раз в 30 с; что слушатели получают — см. «События» ниже). Соединение открывается с первым слушателем, закрывается через `Imap:IdleGrace` после последнего, открывается заново после обрыва с растущей паузой, перезапускает IDLE каждые `Imap:IdleRestart`. Учётные данные берутся у слушателей при каждом открытии (пароль не хранится); слушатель с завершённой сессией или отвергнутым паролем отбрасывается. Лимит `Imap:MaxIdleConnections` отдельный от лимитов рабочих соединений. Исключение в слушателе не мешает остальным. Тесты: модульные (`MailboxWatcherTests`, подставная сессия; `MailboxNoticesTests`) и интеграционные на Dovecot (`MailboxWatchIntegrationTests`: письмо по SMTP, флаги и удаление через doveadm, ожидание дольше `Imap:Timeout` и перезапусков, общее соединение, смена пароля).

- **События ящика (VIN-082; `MailboxEvents.cs` в Core).** Слушатель получает не протокольные уведомления, а события в терминах экрана: `MessageArrived(folder, MessageListItem)` — пришло письмо, со строкой списка (отправитель, тема, дата, флаги: ею можно сразу показать и объявить письмо); `MessagesRemoved(folder, count)` — письма ушли (сервер называет позиции, а не идентификаторы: известно только сколько, список надо перечитать); `MessageMarksChanged(folder, id, seen, flagged, answered, labels)` — отметки письма изменились здесь или в другой программе; `FolderCountersChanged(folder, total, unread)` — счётчики; `FolderStale(folder)` — изменение, которое другие события описать не могут (пачка писем, отметка без идентификатора после удалений): всё, что экран знает о папке, надо перечитать. **Сборка из уведомлений:** пока соединение ждёт (IDLE), по нему нельзя отправить ни одной команды, поэтому уведомления MailKit (`CountChanged`, `MessageExpunged`, `MessagesVanished`, `MessageFlagsChanged`) только собираются в `MailboxNotices` (несколько сообщений об одном письме — одно, побеждает последнее), а первое из них через 250 мс прерывает ожидание — пачка отвечается разом. Между двумя ожиданиями `AnswerAsync` задаёт вопросы: новые письма — `SEARCH` UID больше последнего известного (диапазон `N:*` захватывает и последнее письмо, если оно меньше N, поэтому отбираются только по-настоящему новые) и `FETCH` строк списка; не больше 20 писем за раз (`MaxArrivalsReported`), остальные — `FolderStale`; отметки без UID (Dovecot присылает только позицию) — `FETCH UID` по позиции, но только если в той же пачке ничего не удалялось (позиции сдвигаются), иначе `FolderStale`; счётчики — `Count` и число `UNSEEN`, событие, только если они изменились. События уходят слушателям по порядку: удаления, приход, отметки, счётчики. То, что сервер сказал в ответ на наши собственные вопросы, в следующую пачку не попадает. Подавление эха собственных действий — VIN-087, дельты через CONDSTORE/QRESYNC (там UID удалённых известны) — VIN-086.

- Тесты устойчивости (`ResilienceIntegrationTests`, против настоящего Dovecot): между менеджером и Dovecot стоит `FlakyProxy` (`Vinette.TestSupport`) — обрыв всех соединений, отказ в новых, задержка и «зависание» трафика; плюс настоящий перезапуск Dovecot и смена пароля через `setup email update`. Проверяется: обрыв сети незаметен пользователю, недоступность на несколько секунд переживается повторами, долгая недоступность даёт `MailUnavailableException`, медленная сеть работает, молчащий сервер отсекается по `Imap:Timeout` и следующая попытка проходит, 10 сессий двух ящиков по 10 параллельных команд идут по 10 соединениям, смена пароля завершает сессию при ближайшем переподключении без повторов.

- Метрики (System.Diagnostics.Metrics, meter `Vinette.Mail`; `MailMetrics`): открытые соединения (gauge), открытия, закрытия по причине (`released`, `idle`, `lost`, `cancelled`, `shutdown`), команды в очереди (gauge; ожидание очереди сессии и свободного места), длительность команд (гистограмма, исход `ok`/`error`/`cancelled`), ошибки по виду (`unavailable`, `revoked`, `busy`), повторные попытки. Метки только фиксированные: ни адресов, ни идентификаторов сессий. Экспорт — OpenTelemetry Prometheus (`OpenTelemetry.Extensions.Hosting`, `OpenTelemetry.Exporter.Prometheus.AspNetCore`, Apache-2.0; экспортёр пока публикуется как pre-release): `GET /metrics`, включается `Metrics:Enabled`, закрыт токеном `Metrics:BearerToken` (сравнение по хешам за постоянное время; без токена из 16+ символов приложение не стартует). Endpoint стоит в конвейере до маршрутизации, поэтому политика «нужна сессия» его не касается и он не входит в список анонимных endpoint'ов API; без включения путь `/metrics` отвечает 404. Prometheus: `scrape_configs: - job_name: vinette, authorization: { credentials: <token> }, metrics_path: /metrics`. Публично через обратный прокси `/metrics` открывать не нужно: скрапер ходит во внутреннюю сеть.
- `Session` — запись о вошедшем пользователе: непрозрачный `Id` (256 случайных бит, base64url), адрес, **зашифрованный** пароль, время создания и последней активности. `ToString()` скрывает идентификатор и пароль, чтобы они не попали в логи.
- `ImapAuthenticator` (Vinette.Mail) проверяет пароль командой IMAP LOGIN по короткому соединению: подключение (TLS, обязательный STARTTLS или без шифрования — по `Imap:Security`), команда `ID` с `x-originating-ip` реального клиента, вход, отключение. Сертификат сервера проверяется всегда, кроме явного `Imap:AllowInvalidCertificate`; при отказе от сертификата пароль серверу не отправляется. «Неверный пароль» и «сервер недоступен» — разные исходы; технические причины попадают только в серверный лог.
- Важно для администратора Dovecot: на неверные пароли Dovecot отвечает с задержкой (2 с, при повторных неудачах с одного адреса нарастающей примерно до 15 с). Если Vinette не указан в `login_trusted_networks`, Dovecot видит все входы с адреса Vinette и штрафует **всех пользователей вместе**; с доверенной сетью штраф считается по реальному адресу клиента (`x-originating-ip`, см. `Security:TrustedProxies`). Поэтому `Imap:Timeout` по умолчанию 30 с — больше максимальной задержки, иначе неверный пароль выглядел бы как недоступность почты.
- `ICredentialProtector` шифрует и расшифровывает пароль (Data Protection, реализация в `Vinette.Api`); расшифровка — только в момент открытия соединения с почтовым сервером.
- `SessionService` (Vinette.Api) создаёт сессию (пароль шифруется сразу), проверяет и продлевает её, завершает по простою (`Session:IdleTimeout`) или по абсолютному сроку (`Session:MaxLifetime`); для «Оставаться в системе» оба предела равны `Session:RememberMeLifetime` (30 дней). Просроченные сессии удаляет фоновая очистка раз в минуту. Пароль расшифровывается только методом `RevealPassword` — в момент открытия соединения с почтовым сервером.
- Ключи Data Protection должны лежать на постоянном хранилище (`DataProtection:KeysPath`); без этого при запуске в лог пишется предупреждение, а после перезапуска все пользователи разлогиниваются. Ключи на диске не шифруются (защита — права на каталог), шифрование сертификатом — отдельная задача (VIN-135).
- Вход: `POST /api/v1/auth/login` проверяет учётные данные через `IAuthenticator`, при успехе создаёт новую сессию (идентификатор меняется при каждом входе, прежняя сессия из cookie завершается) и ставит cookie `__Host-vinette_session` (`HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`; без срока, а при «Оставаться в системе» — на `Session:RememberMeLifetime`). Префикс `__Host-` требует HTTPS: на голом HTTP (кроме localhost) браузер cookie не примет, TLS нужно завершать на прокси. `POST /api/v1/auth/logout` завершает сессию на сервере и стирает cookie. Неверный пароль и несуществующий ящик неотличимы (`401 invalid_credentials`), недоступный почтовый сервер — `503 mail_unavailable`.
- Проверка запросов: обработчик аутентификации читает cookie, находит живую сессию через `SessionService` (это же продлевает простой) и создаёт пользователя только с адресом ящика; пароль остаётся в хранилище сессий и доступен коду через `HttpContext.GetSession()`. Политика по умолчанию — «только вошедшим»: любой новый endpoint и SignalR-хаб закрыты, пока их явно не открыли `AllowAnonymous`. Сейчас анонимны только health, вход и выход, файлы брендинга, документ OpenAPI (Development) и раздача SPA; их список зафиксирован тестом. Без сессии — `401 problem+json` (не редирект), недействительная cookie при этом стирается.
- Защита от CSRF (кроме `SameSite=Strict` у cookie сессии): токен ASP.NET Core Antiforgery (на Data Protection) выдаёт `GET /api/v1/csrf` — тело `{ token }` и cookie `__Host-vinette_csrf` (`HttpOnly`, `Secure`, `SameSite=Strict`); SPA держит токен только в памяти и шлёт в заголовке `X-CSRF-Token`. Токен привязан к пользователю, поэтому после входа и выхода клиент берёт новый (клиент `shared/api/client.ts` делает это сам и повторяет запрос один раз при `csrf_failed`). Любой изменяющий запрос также должен прийти со страницы приложения: `Origin` (или `Referer`) сравнивается с адресом запроса по хосту и порту (схема не сравнивается — за прокси с TLS приложение видит http) либо с `Security:TrustedOrigins`; отсутствие обоих заголовков — отказ. SignalR-хаб проверяется только по `Origin` (WebSocket не умеет слать свои заголовки).
- Защита входа от перебора: `LoginAttemptTracker` считает неудачные попытки отдельно по ящику и по IP клиента; после допустимого числа неудач ключ блокируется на 1 минуту, каждая следующая неудача удваивает паузу до потолка (15 минут), успех очищает счётчик ящика, тишина в течение окна (15 минут) — все счётчики. Заблокированный вход отвечает `429` с `Retry-After` и не обращается к почтовому серверу (даже при верном пароле). Отдельно встроенный `RateLimiter` ограничивает число любых попыток входа в минуту с одного IP. Недоступность почтового сервера не считается неудачей. Счётчики — в памяти процесса (на экземпляр), число ключей ограничено. Настройки — `Security:LoginRateLimit:*`. Лимиты по IP осмысленны только при верном определении адреса клиента за прокси (VIN-024).
- Реальный адрес клиента за обратным прокси: `Security:TrustedProxies` — список адресов и подсетей (CIDR) прокси, чьим заголовкам `X-Forwarded-For`, `X-Forwarded-Proto` и `X-Forwarded-Host` верят. Пусто по умолчанию — заголовки игнорируются, middleware не подключается вовсе; `0.0.0.0/0` и `::/0` отклоняются при старте. Цепочку `X-Forwarded-For` читают справа налево, пропуская доверенные узлы; первый недоверенный адрес — клиент, так что подставленное клиентом начало цепочки не учитывается. Петля (`127.0.0.1`) доверенной не считается, пока её не перечислили. Найденный адрес используется в лимитах входа, журнале, поле `ClientIp` каждой записи журнала и команде IMAP `ID` (`x-originating-ip`). Dovecot принимает этот адрес только от доверенных сетей: добавьте адрес Vinette в `login_trusted_networks`. Примеры: Docker-сеть — `172.16.0.0/12`, прокси на том же хосте — `127.0.0.1`; прокси должен ставить `X-Forwarded-For` (дописывать адрес, который видит), `X-Forwarded-Proto` и сохранять или передавать `Host`.
- `ISessionStore` только хранит сессии; таймауты простоя и максимального срока применяет сервис сессий по `LastSeenAt` и `CreatedAt`. Реализация выбирается `Session:Store`: `InMemory` (по умолчанию, один экземпляр, сессии теряются при перезапуске) или `Redis` (`RedisSessionStore`, несколько экземпляров; нужен `Redis:ConnectionString`, без него приложение не стартует). В Redis сессия — хеш `{Redis:KeyPrefix}session:{id}` с зашифрованным паролем (расшифровать его можно только ключами Data Protection, поэтому у всех экземпляров должен быть **общий** `DataProtection:KeysPath`), плюс множество `{prefix}address:{ящик}` для «выйти везде». Ключ живёт `Session:RememberMeLifetime` + 5 минут и исчезает сам; продление «последней активности» — Lua-скрипт, сдвигающий время только вперёд. Идентификатор сессии присутствует в имени ключа, поэтому Redis должен быть доступен только Vinette (сеть, пароль, TLS). Счётчики лимита входа остаются в памяти каждого экземпляра. Пока Redis недоступен, запросы с сессией отвечают `500`, приложение само переподключается.

### Вход на стороне фронтенда

- `features/auth`: `SessionProvider` держит состояние входа (`loading` / `signedIn` / `signedOut`) на `GET /api/v1/me` через TanStack Query; `useSession()` даёт адрес ящика и действия `signIn` / `signOut`. Источник правды — сервер.
- `RequireAuth` оборачивает защищённые маршруты (`/mail/:folder`, `/compose`): без сессии — редирект на `/login` с запоминанием страницы (`state.from`); `RedirectIfSignedIn` не пускает вошедшего на `/login` и возвращает его на запомненную страницу (только внутренние пути: `//хост` и `https://…` игнорируются).
- Глобальный 401: клиент API (`shared/api/client.ts`) вызывает зарегистрированный обработчик при ответе 401 на любой запрос, кроме самого входа (там 401 — неверный пароль). Провайдер в ответ сбрасывает пользователя и удаляет из кэша всё, что принадлежало ему, поэтому следующий пользователь в этом браузере не увидит чужих данных.
- Экран входа (форма) — VIN-026.

Компактная строка — отступы 9 px вместо 14 px, без превью, а запрос идёт с `preview=false`, поэтому серверу не приходится заглядывать в письма; ключ запроса включает `preview`, при возврате к обычной плотности превью догружаются. ## Недоверенный контент

- HTML письма санитайзится на сервере (HtmlSanitizer) и показывается во фронтенде только в `iframe` с атрибутом `sandbox`.
- Внешние изображения заблокированы по умолчанию. Если пользователь попросил их показать, их скачивает сам бэкенд и встраивает в тело как `data:image` (см. «Внешние изображения») — браузер пользователя к серверу отправителя не обращается, адрес и IP не раскрываются.

### Область чтения (`ReadingPane`)

`features/message/ReadingPane` наполняет слот `reader`: по адресу `/mail/:folder/:messageId` запрашивает письмо (`useMessage`, `GET /messages/{id}`, TanStack Query) и показывает: панель действий (`ReaderActionBar`: «Ответить», «Переслать», «В архив», «В спам», «Удалить», «Флажок», «Ещё»), тему 24/700, метки, блок отправителя (аватар 42, имя 15/600 и адрес, «Кому: вы <адрес>» или первые получатели и «и ещё N», дата «Пт, 2 окт., 14:32» — `formatMessageDate`), плашку проверки отправителя (`SenderCheckBadge`: «Отправитель подтверждён» для `verified`, блок-предупреждение «Похоже на мошенничество…» для `suspicious`, ничего для `unknown`), сообщение о скрытых внешних изображениях (если `blockedExternalResources > 0`) и тело в `MessageFrame`, под ним вложения (`AttachmentList`). Состояния: заглушка загрузки, понятная ошибка с «Повторить» (`not_found`, `payload_too_large`, `uid_validity_changed`, недоступность почты), «В письме нет текста», подсказка, если письмо не выбрано. Тема, отправитель и метки выводятся только как текст.

Пока недоступно, но на месте по макету: **«Ответить» и «Переслать» отключены** (`disabled`) до редактора (VIN-102); «В архив», «В спам», «Удалить», флажок и «Ещё» работают (VIN-074, VIN-066). Кнопка «Показать» в сообщении о скрытых изображениях запрашивает письмо с `?images=true` (VIN-059; «Всегда показывать от этого отправителя» — VIN-068). Быстрый ответ (VIN-103) и мобильные уточнения (VIN-067) — позже. `labelColor` перенесён в `shared/lib`, чтобы им пользовались и список, и чтение.

### Вложения в интерфейсе (`AttachmentList`)

Под телом письма: заголовок «Вложения · N» и карточки в две колонки (на телефоне в одну): плашка 38 px с типом файла (расширение заглавными, до 4 знаков; иначе значок файла), имя, размер (`formatBytes`, единицы на языке интерфейса) и значок скачивания. **Карточка — одна ссылка** `<a href="/api/v1/messages/{id}/attachments/{partId}" download>` с именем «Скачать {имя}, {размер}»: доступна по Tab, открывается Enter, фокус-кольцо глобальное. Скачивание — обычный переход по ссылке (а не `fetch`), поэтому cookie сессии передаётся, а ответ сервера всегда `attachment` (HTML и SVG браузер не показывает, а сохраняет). Имена выводятся как текст (на сервере они уже очищены). Проверено в настоящем Chromium: PDF скачивается под своим именем, SVG из «опасного» письма сохраняется, а не открывается.

### Рамка письма (`MessageFrame`)

Единственное место, где содержимое письма попадает на экран (`features/message`). Это третий слой защиты после серверного санитайзера. `iframe` с `sandbox="allow-popups allow-popups-to-escape-sandbox"` — **без** `allow-scripts` (ничего в письме не исполняется) и **без** `allow-same-origin` (у страницы нет доступа к приложению, cookie и хранилищу); ссылки открываются в новой вкладке, которая сама не в песочнице, чтобы сайты за ссылками работали. Содержимое идёт через `srcdoc`, `referrerpolicy="no-referrer"`, имя рамки (`title`) обязательно. Внутри страницы первым стоит собственная CSP: `default-src 'none'; script-src 'none'; img-src data:; style-src 'unsafe-inline'; font-src/connect-src/media-src/object-src/frame-src 'none'; base-uri 'none'; form-action 'none'` — скрипты запрещены совсем, из сети ничего (картинки только `data:`, поэтому встраивание `cid:` на сервере и нужно), стили только встроенные (письмо верстается само). Базовые стили страницы — 15/1.65, цвета из токенов приложения (читаются из CSS-переменных, рамка их не видит), для `text` — ширина до 68ch (DESIGN.md §5), `<base target="_blank">`.

**Высота.** Без скриптов и без доступа к документу страница не может сообщить, какой она высоты (`allow-same-origin` запрещён), поэтому «автоподбор по содержимому» невозможен: рамка заполняет отведённое ей место (`h-full w-full`, минимум 240 px) и прокручивается внутри.

Защита закреплена тестами: атрибуты `sandbox` (нет ни одного из `allow-scripts`, `allow-same-origin`, `allow-forms`, `allow-top-navigation`, `allow-modals`, `allow-downloads`), политика (ни `unsafe-eval`, ни `unsafe-inline` для скриптов, ни адресов сети), враждебная разметка остаётся текстом атрибута `srcdoc` и не попадает в страницу; тест `no-raw-html.test.ts` проверяет, что нигде в исходниках нет `dangerouslySetInnerHTML`, `innerHTML =`, `insertAdjacentHTML`, `document.write`; Playwright-сценарий `e2e/message-frame.spec.ts` открывает в настоящем Chromium рамку с вредоносным письмом (`<script>`, `onerror`, ссылка `javascript:`) и проверяет, что ничего не выполнилось (нет запросов, диалогов и следов в документе рамки).

### Санитайзер HTML

`IMessageHtmlSanitizer` (Core) / `MessageHtmlSanitizer` (Mail, пакет HtmlSanitizer, MIT). Это первый из трёх слоёв: дальше идут `iframe` с `sandbox` без `allow-scripts` и `allow-same-origin` и собственная CSP внутри `srcdoc` (VIN-063). Результат — `SanitizedHtml(Html, BlockedExternalResources, Truncated, Rejected, ExternalImages)`; HTML без санитайзера наружу не отдаётся. Правила — белый список, всё остальное удаляется (вместе с содержимым, чтобы текст скриптов и стилей не превращался в видимый):

- **Теги:** `a abbr acronym address article aside b bdi bdo big blockquote br caption center cite code col colgroup dd del dfn div dl dt em figcaption figure font footer h1–h6 header hr i img ins kbd li main mark nav ol p pre q s samp section small span strike strong style sub sup table tbody td tfoot th thead tr tt u ul var wbr`. Нет: `script iframe frame object embed applet form input button select textarea svg math meta base link template noscript video audio` и всё неизвестное.
- **Атрибуты:** `align alt bgcolor border cellpadding cellspacing class color colspan dir face height href hspace id lang nowrap rowspan size src start style title valign vspace width span type`. Нет `on*`, `data-*`, `name`, `ping`, `download`, `srcset`, `background`, `contenteditable`, `tabindex`, `accesskey`, `hidden`. `target` и `rel` ставит сам санитайзер на каждую ссылку (`_blank`, `noopener noreferrer`).
- **Ссылки (`a href`):** только `http`, `https`, `mailto`, `tel` и якоря `#…`; `javascript:`, `vbscript:`, `data:`, `file:`, `ftp:`, `//host` и относительные пути удаляются (текст ссылки остаётся).
- **Картинки (`img src`):** `cid:…` остаётся (часть самого письма, VIN-060), `data:image/png|jpeg|gif|webp;base64` до 1 МБ остаётся (внешней сети не касается); SVG, любые другие `data:`, `http`/`https`/`//` удаляются, а внешние считаются в `BlockedExternalResources` — по этому числу фронтенд предлагает «Показать изображения» (прокси — VIN-059). Фоны таблиц (`background`), `srcset`, `poster` — то же самое.
- **CSS (атрибут `style` и блоки `<style>`):** белый список свойств (цвет, шрифт, отступы, границы, размеры, выравнивание, `display`, `float`, `overflow`, `visibility`, `white-space`, `opacity` и т. п.). Нет `position`, `z-index`, `content`, `filter`, `behavior`, `-moz-binding`, `background-image`. Правила `@media` и обычные остаются; `@import`, `@font-face`, `@namespace` и прочие at-правила удаляются. Любая декларация с `url(`, `image-set(`, `expression(`, `javascript:`, `behavior:`, обратной косой чертой (CSS-экранирование) удаляется целиком — после работы библиотеки это проверяется ещё раз по тексту результата.
- **Ограничения:** вход длиннее 1 000 000 символов обрезается (`Truncated`); вложенность элементов глубже 200 отклоняется заранее (`Rejected`, показывается текст) — глубокое дерево может исчерпать стек, а это исключение не перехватить. На любой вход санитайзер не бросает исключений; повторная очистка результата ничего не меняет.

Набор известных XSS-векторов (366 штук: скрипты, обработчики событий, опасные адреса, кодировки, SVG и MathML, CSS, `data:`, mutation XSS, формы и встраиваемые объекты, странности разбора атрибутов, внешние загрузки и обычные письма) — данные в `backend/tests/fixtures/xss/vectors.json`, формат в README рядом. Тест `XssVectorTests` разбирает результат заново, как браузер, и судит по дереву; новый вектор добавляется данными без правки кода.

## White-label

Брендинг (`Branding:*`: название, логотип, favicon, акцентный цвет, подпись, «Powered by») берётся из конфигурации и подставляется сервером прямо в `index.html`: `<title>`, favicon и JSON-блок `<script id="vinette-config" type="application/json">` с настройками. Фронтенду не нужен отдельный запрос до первого рендера. Логотип и favicon из файлов отдаются по `/branding/logo` и `/branding/favicon`.

## Конфигурация

Слои по возрастанию приоритета: `appsettings.json` → переменные окружения `VINETTE_*` (вложенность через `__`) → необязательный файл из `VINETTE_CONFIG`. Классы Options валидируются при старте — с неверной конфигурацией процесс не запускается.

## Ошибки API

Все ошибки `/api/v1` — ProblemDetails (RFC 9457) с полями `code` и `correlationId`; идентификатор запроса также возвращается в заголовке `X-Correlation-Id` и пишется в логи. Каталог кодов и формат — в [api-errors.md](api-errors.md).

## Развёртывание

Один артефакт: Docker-образ (multi-arch amd64/arm64, порт 8080, non-root) или публикация `dotnet publish` под systemd. Образ раздаёт собранный фронтенд из `wwwroot` того же процесса.
