# Безопасность образа

Как устроен образ Vinette, как его запускать с минимумом прав, как CI проверяет его на известные уязвимости и как проверить подпись и состав скачанного образа (VIN-123).

## Что в образе

- Основа — урезанный образ среды .NET (`aspnet:…-chiseled`): нет оболочки, менеджера пакетов и `curl`; в образе лежат только среда выполнения и само приложение.
- Процесс запускается **не от root** (пользователь `1654`), слушает порт 8080 (непривилегированный).
- Всё, что приложение пишет (ключи Data Protection, настройки, вложения, отложенные письма, временные файлы), лежит в `/data` — единственном месте для записи ([backup-and-update.md](backup-and-update.md)).
- Проверка работоспособности делает само приложение (`--healthcheck`).

## Запуск с минимумом прав

Образ работает с корневой файловой системой «только для чтения», без привилегий Linux и без повышения прав:

```bash
docker run -d --name vinette -p 8080:8080 \
  --read-only --cap-drop ALL --security-opt no-new-privileges:true \
  -v vinette-data:/data \
  -e VINETTE_Imap__Host=mail.example.com -e VINETTE_Smtp__Host=mail.example.com \
  ghcr.io/f1nn17/vinette:latest
```

Те же ограничения стоят в [compose.yaml](../deploy/docker/compose.yaml) (`read_only`, `cap_drop: ALL`, `no-new-privileges`). Отдельный `tmpfs` для `/tmp` не нужен: каталог временных файлов (`TMPDIR`) указывает на `/data/tmp`. Том `/data` обязателен — без него ключи теряются при каждом пересоздании контейнера.

Проверено на настоящем контейнере с этими флагами: вход, чтение, отправка, черновики, отложенные письма, настройки, метки и политика безопасности (сквозные тесты Playwright), в журнале нет ошибок. В CI проверка политики безопасности идёт против образа, запущенного с теми же флагами.

Что ещё стоит ограничить на своей стороне (это уже платформа, не образ): лимиты памяти и процессора (`--memory`, `--cpus`), сеть только до почтового сервера и обратного прокси.

## Скан уязвимостей

Каждая сборка в CI и каждый релиз проверяются [Trivy](https://github.com/aquasecurity/trivy) (лицензия Apache-2.0): пакеты операционной системы образа и зависимости .NET (по `*.deps.json`). Скрипт — [scripts/scan-image.sh](../scripts/scan-image.sh); Trivy запускается из собственного образа, закреплённого по версии и дайджесту, поэтому нужен только Docker.

- **Критическая уязвимость (CRITICAL), для которой уже есть исправление, останавливает сборку и релиз.** В релизе проверка идёт до публикации: ничего не попадёт в реестр.
- Уязвимости HIGH выводятся в журнал сборки, но не останавливают её: исправления для них часто приходят с обновлением основного образа, а не с нашим изменением. Смотрите их при каждом релизе.
- Уязвимости без исправления выводятся в списке, но не останавливают сборку (исправлять нечего).
- Принятое решение «эта находка нас не касается» записывается в [.trivyignore](../.trivyignore) с причиной и датой, когда посмотреть снова. Сейчас файл пуст.

Проверить самому:

```bash
make docker                                   # образ vinette:dev
sh scripts/scan-image.sh vinette:dev          # список и ворота
sh scripts/scan-image.sh vinette:dev sbom.json   # и состав образа в sbom.json
```

Когда проверка упала: обновите основной образ (пересоберите без кэша — новые исправления приходят вместе с ним) или обновите зависимость, названную в таблице. Скан — снимок на день сборки: новые уязвимости находят позже, поэтому образ стоит пересобирать и обновлять (раздел об обновлении в [backup-and-update.md](backup-and-update.md)).

## SBOM — состав образа

К каждому релизу прикладывается список компонентов образа в формате SPDX JSON (`vinette-X.Y.Z.spdx.json` на странице релиза), и тот же список подписан и привязан к образу. Он нужен, чтобы быстро ответить на вопрос «затронут ли мой образ новой уязвимостью» без распаковки образа: вторым сканером, учётной системой компании или поиском по файлу.

## Подпись образа

Релизный образ подписан [cosign](https://github.com/sigstore/cosign) без ключей («keyless»): подпись выдаётся на лету по идентификатору рабочего процесса GitHub Actions и записывается в публичный журнал Sigstore. Хранить и менять ключ не нужно, а проверка показывает, что образ собран именно рабочим процессом `release.yml` этого репозитория по тегу `vX.Y.Z`, а не загружен вручную.

Проверить подпись перед запуском (нужен [cosign](https://docs.sigstore.dev/cosign/system_config/installation/)):

```bash
cosign verify ghcr.io/f1nn17/vinette:0.1.0 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-identity-regexp '^https://github.com/F1nn17/Vinette/\.github/workflows/release\.yml@refs/tags/v'
```

Проверить и получить SBOM, привязанный к образу:

```bash
cosign verify-attestation ghcr.io/f1nn17/vinette:0.1.0 --type spdxjson \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-identity-regexp '^https://github.com/F1nn17/Vinette/\.github/workflows/release\.yml@refs/tags/v'
```

Подпись ставится на дайджест образа, поэтому она действует для всех его тегов (`0.1.0`, `0.1`, `latest`). Для самых строгих установок запускайте образ по дайджесту (`ghcr.io/f1nn17/vinette@sha256:…`), а не по тегу.

## Чего здесь нет

- Подписи и SBOM появляются с первым релизом (VIN-133, VIN-134): рабочий процесс проверен на синтаксис и по частям (скан и SBOM на настоящем образе, ворота падают на заведомо уязвимом образе), а целиком он впервые пройдёт на пробном теге.
- Сканируется образ, а не зависимости исходников: уязвимости пакетов NuGet и npm проверяются отдельно (`dotnet list package --vulnerable`, `pnpm audit`; результаты — в [security-audit.md](security-audit.md)).
- Ежедневного скана уже выпущенных образов нет: об уязвимости в опубликованном образе скан не расскажет, пока не соберётся новый.
