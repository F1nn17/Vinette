# Резервное копирование, восстановление и обновление

Vinette не хранит почту (она на вашем почтовом сервере и копируется вместе с ним), но у него есть собственные данные: ключи шифрования паролей, настройки пользователей и очередь отложенных писем. Их нужно копировать. Этот документ — что, как и когда, как восстановиться и как обновляться.

## Что копировать

| Что | Где (в образе) | Зачем копировать | Что будет без копии |
| --- | --- | --- | --- |
| **Ключи шифрования** | `DataProtection:KeysPath` (`/data/keys`) | без них не расшифровать сохранённые пароли | все выходят из системы; письма из очереди отложенной отправки не отправятся (останутся без пароля и при следующем входе владельца ящика перенесутся в «Черновики») |
| **Сертификат ключей** и его пароль (если ключи зашифрованы, [data-protection-keys.md](data-protection-keys.md)) | где вы его храните | без него зашифрованные ключи не прочитать | то же, что без ключей |
| **Настройки пользователей** | `Settings:Path` (`/data/settings`) | подписи, язык, плотность, цвета меток, доверенные отправители | пользователи начинают с настроек по умолчанию |
| **Очередь отложенной отправки** | `Scheduling:Path` (`/data/scheduled`) | письма, которые ждут своего часа | отложенные письма пропадут |
| **Ваша конфигурация** | файл `VINETTE_CONFIG`, переменные окружения или `compose.yaml`, файлы логотипа и значка, конфигурация прокси | чтобы поднять тот же сервис заново | придётся собрать настройки заново |

Не нужно копировать: сессии (в памяти или Redis: после восстановления все войдут заново), `Attachments:Path` (загруженные, но ещё не отправленные файлы живут до суток, их достаточно прикрепить заново; копируйте, только если не хотите терять и их), письма (это почтовый сервер).

Ключи меняются редко (новый ключ раз в 90 дней), настройки и очередь чаще. Копируйте **весь том `/data` целиком**: так ничего не забудется, а размер маленький.

**Сертификат и каталог ключей храните в разных местах.** Если копия каталога лежит рядом с сертификатом, шифрование ключей ничего не защищает. Копию сертификата сделайте отдельно и обязательно: без него ключи и всё, что ими зашифровано, потеряно.

## Как делать копию

Лучше всего **остановить приложение на минуту**: тогда набор файлов точно согласован (у каждого отложенного письма два файла, описание и само письмо, и их копия «на лету» может разойтись). Если останавливать нельзя, копируйте в тихое время и учтите это при восстановлении.

Docker (том `vinette-data`, копия в текущий каталог):

```bash
docker stop vinette
docker run --rm -v vinette-data:/data -v "$PWD":/backup alpine tar czf /backup/vinette-data-$(date +%F).tgz -C /data .
docker start vinette
```

Голое железо (данные в `/var/lib/vinette`, пользователь `vinette`):

```bash
sudo systemctl stop vinette
sudo tar czf vinette-data-$(date +%F).tgz -C /var/lib/vinette .
sudo systemctl start vinette
```

Храните копии не на той же машине. Для проверки списка: `tar tzf vinette-data-….tgz` покажет `keys/`, `settings/`, `scheduled/` (и `attachments/`).

## Как восстановиться

1. Подготовьте то же, что было: образ той же или более новой версии, конфигурацию, сертификат ключей (если был), прокси.
2. Положите данные в **пустой** том или каталог **с теми же правами** (владелец — пользователь процесса: в образе UID 1654, на голом железе `vinette`; tar от root сохраняет владельца, как в командах ниже).
3. Запустите.

Docker (новый том `vinette-data`):

```bash
docker volume create vinette-data
docker run --rm -v vinette-data:/data -v "$PWD":/backup alpine tar xzf /backup/vinette-data-2026-11-28.tgz -C /data
docker run -d --name vinette -p 8080:8080 -v vinette-data:/data  ...  ghcr.io/f1nn17/vinette:0.1.0
```

Голое железо:

```bash
sudo tar xzf vinette-data-2026-11-28.tgz -C /var/lib/vinette
sudo chown -R vinette:vinette /var/lib/vinette && sudo chmod 700 /var/lib/vinette
sudo systemctl start vinette
```

После запуска: в журнале нет ошибок; пользователи входят заново (сессии не копируются); настройки и подписи на месте; в «Отложенных» письма из очереди.

### Что при восстановлении теряется

- **Всё, что изменилось после копии:** настройки и письма, поставленные в очередь после копии, пропадут. А письма, которые были в очереди на момент копии и **уже ушли после неё**, в восстановленной очереди окажутся снова и **уйдут второй раз**: проверьте очередь («Отложенные») сразу после восстановления и отмените те, что уже отправлены (они лежат в «Отправленных»).
- **Сессии.** Все входят заново (то же при обычном перезапуске с сессиями в памяти).
- **Если копия без ключей** (или ключи не расшифровываются): настройки остаются, а письма из очереди не отправятся: пароль ящика, которым они зашифрованы, не прочитать. Они остаются в очереди без пароля, а при следующем входе владельца ящика переносятся в «Черновики» с пометкой.

## Проверено

На настоящем контейнере (Vinette `vinette:dev`, настоящий Dovecot и Postfix): в работающей установке поставлена подпись, плотность «компактная» и письмо, отложенное на 80 секунд; приложение остановлено, том упакован `tar`; контейнер и том **удалены**; данные распакованы в новый том и запущен новый контейнер. Результат: тот же файл ключа и те же владелец и права, в журнале нет ошибок, настройки (плотность, подпись) на месте, письмо в очереди, и **оно ушло в назначенное время** (найдено в «Отправленных» и во «Входящих»): то есть восстановленные ключи расшифровали сохранённый пароль.

## Обновление

Данные между версиями остаются на месте (том `/data`), поэтому обновление — это замена образа или файлов приложения.

1. **Прочитайте `CHANGELOG.md`** за версии между вашей и новой: там сказано, какие настройки появились, что изменилось в поведении, формате данных или API. Особое внимание разделам `Changed`, `Removed`, `Security`.
2. **Сделайте копию** `/data` (как выше), особенно перед версиями, где в CHANGELOG что-то сказано про данные.
3. **Укажите точную версию** образа (`ghcr.io/f1nn17/vinette:0.1.0`), не `latest`: так обновление происходит, когда вы решили, и откат — это возврат прежнего тега. Образ публикуется тегами `X.Y.Z`, `X.Y` и `latest`.
4. Замените образ и перезапустите (`docker compose pull && docker compose up -d`); на голом железе — подмените каталог `/opt/vinette` новой версией и `systemctl restart vinette`.
5. **Проверьте:** `GET /api/v1/health` отвечает `ok` с новой версией, в журнале нет ошибок и новых предупреждений, вход и чтение работают.

Что происходит при перезапуске: сессии в памяти теряются (все войдут заново; с `Session:Store = Redis` нет), открытые страницы покажут «нет связи» и переподключатся сами, письма из очереди остаются на месте (после старта уходят те, чей час настал).

Версии до 1.0 могут менять формат данных между выпусками: поэтому пункты 1 и 2 обязательны.

### Несколько экземпляров

Обновляйте по одному. Очередь отправляет **один** экземпляр (`Scheduling:Enabled = true`): пока он перезапускается, письма не уходят (уйдут сразу после старта, ничего не теряется). Остальные можно обновлять без остановки сервиса за балансировщиком. Не запускайте одновременно экземпляры разных версий дольше, чем нужно: они делят одни каталоги данных.

## Откат

1. Верните прежний тег образа (или прежние файлы) и перезапустите.
2. Если новая версия что-то записала в данные, чего прежняя не читает (в CHANGELOG об этом сказано), остановите приложение и **восстановите том из копии**, сделанной перед обновлением (как выше): всё, что менялось после неё, потеряется.
3. Проверьте, как после обновления.

## Памятка

- Копия `/data` по расписанию и перед каждым обновлением; хранить вне машины.
- Сертификат ключей и его пароль — отдельная копия, отдельное место.
- Раз в квартал восстановите копию на тестовой машине и убедитесь, что настройки на месте, а письмо из очереди уходит: копия, из которой не пробовали восстанавливаться, не копия.
- Копии почты — это резервное копирование вашего почтового сервера, не Vinette.
